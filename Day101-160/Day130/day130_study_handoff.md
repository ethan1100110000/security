## TPAR 입력·처리·출력

입력은 매직 TPAR, version, command, length, payload 순서다. 헤더는 총 7바이트다.

1. Day115 파일 하네스는 경로를 받아 `open`으로 파일 디스크립터를 얻고, `read`로 지역 배열 `input[256]`에 읽는다.
2. `received`는 실제 읽힌 바이트 수다. 음수 반환을 검사한 뒤 입력의 시작 주소와 실제 읽은 길이를 파서에 전달한다. 배열 용량 256을 실제 길이로 전달하지 않는다. 한 번의 read가 항상 파일 전체를 읽는다는 보장은 없다.
3. 파일 디스크립터를 닫아도 지역 배열에 이미 읽힌 데이터는 남아 있으며, main의 해당 블록이 살아 있는 동안 파서가 사용할 수 있다.
4. 파서는 헤더 최소 길이와 형식을 확인하고, 헤더의 length가 실제 입력의 남은 데이터보다 크지 않은지 확인한다.
5. 복사 목적지 payload의 용량도 별도로 확인한 뒤 복사·출력을 수행한다.

범위 조건은 헤더 크기 확인 후 `length <= input_size - 7`로 입력 쪽 범위를, `length <= sizeof(payload)`로 목적지 배열의 범위를 확인하는 것이다. 원래 사례의 원인은 목적지 용량 검사가 빠진 것으로, 단순히 모든 length 검사가 없었다고 표현하지 않는다.

## 사용자가 연결해서 설명한 내용

- 하네스는 input의 시작 주소와 실제 input_size를 파서에 전달한다. 헤더의 length만으로 그만큼의 데이터가 실제 존재함을 보장할 수 없다.
- 기존 코드에서 length와 payload 배열 크기 비교가 빠져 범위 밖 쓰기가 발생할 수 있었다.
- 수정 코드는 복사 전에 목적지 용량을 비교하고, 크기 초과 시 복사를 거부하도록 한다.
- 중간에 널바이트가 있어도 바이트 수를 지정하는 복사·출력은 그 위치에서 멈추지 않는다.
- 두 정상 입력의 결과만으로 목적지 용량 초과 거부 분기까지 실행·검증했다고 할 수 없다.

사용자는 한 문단으로 위 흐름을 설명했다. 두 번째 정상 입력을 A/널/C/D로 잘못 회상하여 실제 A/널/B/C로 교정했다. 직접 관찰한 것은 stdout의 출력 바이트이며 memcpy의 역할과 fwrite의 역할도 구분했다.

| Payload | 실제 payload 출력 바이트 | 나머지 stdout | 종료 코드 | stderr |
|---|---|---|---|---|
| A B C D | 41 42 43 44 | 줄바꿈 및 state=6 줄 | 0 | 없음 |

## CS: 크기와 수명

### 실제 sizeof 관찰

별도 정상 C 프로그램에서 다음을 관찰했다.

| 표현 또는 인자 | 관찰값 |
|---|---:|
| 호출자 지역 uint8_t input[256]의 sizeof(input) | 256 |
| 호출자 sizeof(input[0]) | 1 |
| 포인터 인자를 받은 함수의 sizeof(input) | 8 |
| 그 함수의 sizeof(input[0]) | 1 |
| 의도적으로 전달한 input_size | 5 |

이 프로그램은 read 실험이 아니며 5는 직접 전달한 인자값이다. 인자를 20으로 바꾼 경우의 sizeof=8, size=20은 사용자의 예측으로, 별도 실행 결과가 아니다. 포인터 8바이트는 확인한 환경의 값이며 모든 환경에 일반화하지 않는다.

### 확인한 답과 교정

- 실제 5바이트를 읽은 배열의 용량이 256이라도 input_size는 5다.
- char *payload에서 sizeof(payload)는 포인터 변수의 크기이며, sizeof(*payload)는 char 하나의 크기인 1이다. 사용자는 처음 sizeof(*payload)를 전체 크기로 추측하고 char를 2바이트로 답했으며 힌트 후 교정했다.
- 포인터로 복사 목적지를 받으면 전체 버퍼 용량을 별도로 받아야 한다. 입력의 실제 길이와 출력 공간의 용량은 역할이 다르다.
- 주소와 크기가 정확해도 이미 free된 메모리는 사용할 수 없다.
- 지역 배열은 해당 블록을 벗어나면 수명이 끝난다. 주소 반환이 수명을 연장하지 않는다.
- 호출자가 만든 살아 있는 버퍼를 함수가 채우면 그 함수 반환 후에도 호출자 블록의 수명 동안 결과를 사용할 수 있다. 쓰기 범위를 제한하려면 용량도 전달한다.
- 앞선 복습에서 free 후 다른 포인터 별칭의 주소가 자동으로 바뀌지 않음, vector가 소유한 저장소와 외부 포인터 수명이 다름, 재할당 후 외부 포인터가 자동 갱신되지 않음을 다뤘다.
- ASan이 할당된 살아 있는 버퍼 내부의 논리적 입력 길이 위반을 모두 탐지하지는 않는다는 점을 설명했다.

## 앞서 다룬 보안 전반 복습

- 타겟 프로그램의 계측이 coverage를 기록하고 AFL++가 이를 읽는다. 공유 영역 외에 모든 일반 메모리가 자동 공유되는 것은 아니다.
- 새 coverage는 새로운 계측 경로의 관찰이지 오류 발생의 증명이 아니다. 같은 coverage라도 입력 데이터·접근 주소가 달라 메모리 오류 여부가 달라질 수 있다.
- coverage 항목 개수만 같다고 항목 자체가 같다는 보장은 없다.
- 입력 형식 오류의 정상 반환과 crash를 구분한다. 종료 코드만으로 거부 원인이나 메모리 오류 종류를 확정하지 않는다.
- 소스 수정이 기존 실행 파일에 적용되려면 다시 빌드해야 한다.
- GDB의 실패 위치와 근본 원인은 다를 수 있으며 이전 상태 변경을 추적해야 한다.
- rwx 권한과 입력 파일의 읽기 권한을 설명했다.
- read의 음수 오류를 size_t로 변환하기 전에 검사하고, 바이너리 실제 길이를 strlen으로 대신하지 않는다.
