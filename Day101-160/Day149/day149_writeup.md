# Day149 — Submit 입력 경계·Canary 탐지 조건 검증
2026-11-10 / W05 3/5 / 로컬 `archive_desk` GDB 실측과 문답

## 연구 질문과 환경
메모리 경계 위반과 stack canary 검사의 실패는 동일한 현상인가? 입력 길이·입력 바이트가 각각 어떤 영향을 주는지 확인한다. 분석 대상은 사용자가 로컬 WSL에서 실행한 [Day147의 `archive_desk`](../Day147/README.md)로, 소스 `record[48]`, 요청 `read(...,112)`, PIE/Canary 활성화 환경이다. 입력 파일 생성·브레이크포인트 배치·해석에는 교사 안내가 있었고 실제 GDB 및 실행 출력은 사용자가 제출했다.

메모리 구조는 로컬 역어셈블에서 확인된 Submit `record` 시작 `rbp-0x40`, 스택 Canary `rbp-0x8`를 토대로 구성한다:
```text
낮은 주소
[record 48B]         rbp-0x40 .. rbp-0x11
[정렬용 padding 8B]  rbp-0x10 .. rbp-0x9
[canary 8B]          rbp-0x8  .. rbp-0x1
[saved RBP 8B]       rbp
[saved RIP 8B]       rbp+0x8
높은 주소
```
`read` 요청 최대 112B와 실제 반환 바이트 수는 다르다. 사용자 예상에서 처음 48/56B와 Canary의 거리를 혼동했으나, **48B는 버퍼 끝, 56B는 padding 끝, 57번째 바이트가 Canary 첫 바이트**임을 교정했다.

## 입력 길이 통제와 실제 관찰
각 파일은 메뉴 선택용 `b"2\n"` 다음에 `b"A"*N`을 배치했다. 다음은 사용자가 실행해 보고한 결과다.

| Submit 입력 N | 메모리 기준 예상 | 사용자 실행 결과 |
| --- | --- | --- |
| 48 | `record[48]` 안만 기록 | `received: 48` / 정상 종료 |
| 56 | `record[48]` + padding 8B 기록 | `received: 56` / 정상 종료 |
| 57 | Canary 첫 1B까지 기록 | `stack smashing detected` |

56B에서도 선언한 버퍼의 범위는 이미 넘는다. **정상 반환은 안전한 복사를 뜻하지 않는다.** 57B의 입력 값은 `'A'=0x41`이므로 Canary 저장값을 변경할 것이라고 예상했다. 57B 실행에서 `received:`의 정확한 출력은 사용자가 제출하지 않았으므로 관찰했다고 적지 않는다.

## GDB로 Canary 저장값과 원본 바이트 비교
교사 안내로 Submit 검사 전 `b *0x555555555406`에 중단하고(이 주소는 해당 PIE 실행에만 유효), 사용자가 제출한 정확한 출력:
```gdb
pwndbg> x/8bx $rbp-0x8
0x7fffffffdf58: 0x41 0x94 0xdf 0x1b 0xbf 0xad 0xff 0x9b
pwndbg> x/8bx $fs_base+0x28
0x7ffff7fb1768: 0x00 0x94 0xdf 0x1b 0xbf 0xad 0xff 0x9b
```
낮은 주소 첫 바이트 하나만 `00→41`로 변경됐으며 나머지 7B는 일치한다. 사용자는 바뀐 바이트를 스스로 지목했다. 함수가 저장 Canary와 TLS 원본을 비교할 때 불일치가 발생해 `__stack_chk_fail`로 이어진다는 해석과 부합한다.

## CS·조건 변경: 같은 길이, 다른 마지막 바이트
새 조건 `b"A"*56 + b"\x00"` (총 57B). 사용자는 **메모리 경계는 넘지만 원래 Canary 첫 바이트 `0x00`과 같은 값을 쓰므로 Canary 비교는 통과할 것**이라 예상했다. 실제 실행도 교사의 `received: 57` 및 정상 종료 여부 질문에 예상대로라고 응답했다.

따라서 경계 침범 여부, 보호기법의 탐지 여부, 실행흐름 제어 성공은 반드시 분리한다. 이 실행은 탐지 여부에 대한 재검증이며 RIP 제어 또는 완전한 익스플로잇 성공의 증거는 아니다.

## 보안 2회독: Day081 실행 가능한 함수 포인터의 조건
[Day081 write-up](../../Day040-100/Day081/write_up.txt)을 직접 대조했다. glibc 2.35 환경에서 `__free_hook`은 호환성 심볼로 남아 있고 쓰기 가능했으나 **실제 `free()` 실행 경로에서 사용되지 않았다**. 사용자는 이 차이를 과거 기록 없이 먼저 회상했고, 기록과 대조해 확인했다.

대체 대상 함수 포인터는 주소 파악·쓰기 가능성뿐 아니라 **나중에 실제 호출되는지**, **인자와 ABI·함수 타입이 호환되는지**를 살펴야 한다. 예를 들어 `int (*action)(const char *) = puts;`라면 적합한 조건에서 `system`도 동일한 함수 시그니처를 가진다. 처음 교사가 제시했던 `void (*action)(char *) = puts`는 반환형·매개변수의 `const` 일치가 없어 엄밀한 C 타입 예시로는 부정확했으며 수업 중 바로잡았다.

조건 변경 `void (*action)(int)`를 `system` 주소로 변경한 경우, `system(const char *)`와 **호출 타입이 불일치**한다. C에서는 호환되지 않는 타입을 통해 함수를 호출하면 정의되지 않은 동작이며, x86-64 ABI에서도 전달한 정수가 유효 문자열 포인터라는 보장이 없다. 사용자도 정상 호출을 보장할 수 없다고 답했다. 이 반례는 문답이며 실제 실행한 사례가 아니다.

- **동적 메인:** 사용자 직접 실행의 길이별 관찰 및 `rbp-0x8` vs `$fs_base+0x28` 메모리 덤프가 있다.
- **CS:** null 바이트 조건의 예상 및 사용자 정상 종료 보고. 별도 C 컴파일 실험은 아니다.
- **복습:** Git Day081 기록과 대조, 사용자 회상 및 새 함수 시그니처 반례 답변. 과거 실습 재실행 없음.
- **교사 도움:** 파일 생성 명령, breakpoint 명령, Canary/padding 교정, 함수 포인터 시그니처 보완과 마지막 반례.
- **미확인:** 전체 GDB 원본·로컬 파일과 도구 버전/바이너리 해시/소요 시간은 저장소에서 확인 불가. W05 3/5의 최신 엑셀 바이너리 행은 GitHub 도구 UTF-8 디코딩 오류로 이번 세션에서 직접 열람하지 못했으며, 이 문서는 **이번 대화의 실제 수행 범위**를 기록한다. 새로운 exploit 성공이나 무힌트 전체 숙달을 주장하지 않는다.

## 2026-11-12 보완 — CS 정수 변환과 배열의 로컬 실행 검증
**원래 엑셀 Day149 CS 필수 과제 보완**. 이전에는 Canary 조건 변경이 CS를 대체해 정수 변환·배열의 로컬 실행 증거가 없었다. 사용자에게 작은 C 프로그램을 제시하고 예상→GCC 실행→결과 대조를 요청했으며, 사용자 로컬 WSL에서 다음을 보고했다.

코드 구조는 [참고 소스 bounds_cs_reference.c](bounds_cs_reference.c)에 보존했다. 이는 교사가 앞서 제시한 코드의 재구성본이다. 사용자 로컬의 `bounds_cs.c`와 바이너리 bytes가 직접 업로드된 것은 아니다.

```text
$ gcc -std=c11 -O0 -Wall -Wextra bounds_cs.c -o bounds_cs
$ ./bounds_cs
A = 0
B = -3
C = -4
D = -2
```

사용자는 **"결과고 예상대로 나왔어"**라고 답했다. 미리 네 개의 개별 예상값을 적어 제출한 기록은 없고, 본인이 예상과 일치했다고 보고한 것으로 구분한다.

| 구분 | input_size | len | 수행 경로 | 결과 |
| --- | ---: | ---: | --- | --- |
| A | 12 | 8 | 헤더 4B 제외 원본 8B; 목적지 8B; 양쪽 동일 경계 허용 | 0 |
| B | 12 | 9 | 원본 8B보다 len9가 크므로 원본 길이 검사에서 거부 | -3 |
| C | 20 | 9 | 원본 16B가 충분하지만 목적지 8B보다 len9가 커 목적지 검사에서 거부 | -4 |
| D | 20 | -1 | 부호 있는 음수는 size_t 변환 전에 거부 | -2 |

기존 필수 공부의 **실행 관찰·조건 분기 비교**는 이 로컬 결과로 확인. 모든 배열 접근/입력 조합의 안전성을 증명한 것은 아니다. 사용자가 결과와 예상이 일치했다고 진술했으므로 이번 추가 세트에는 실제 오답 사례가 없으며, 이전 Day147/Day146의 signed/unsigned와 길이 누락 교정 사례를 연결해 기록했다. 새로 틀린 답을 지어내지 않았다.
