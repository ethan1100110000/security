# Day150 — Submit 버퍼 크기 조건 변경과 크래시 원인 분류
2026-11-11 / W05 4/5 / 사용자 로컬 코드·GDB·실행 결과 기반

## 목표와 환경
이전 Day149에서는 `record[48]`으로 57번째 입력 바이트가 Canary의 첫 바이트에 도달했다. 이번에는 사용자 로컬의 Day147 소스를 **별도 Day150 디렉터리에 복사하고 `record[48]`을 `record[64]`로만 바꾼 뒤**, 바이너리의 새 메모리 경계를 찾고 입력값을 바꿔 재검증했다.

- C 소스: `Day147/challenge.c`의 `submit()`에서 `char record[64]`; `receive_bytes(record,112)`는 유지. Full RELRO/Canary/NX/PIE 빌드 스크립트를 복사해 사용했다고 보고.
- 원본 보존: 기존 Day147 소스/바이너리를 수정하지 않고 Day150 로컬 경로에서 실행했다.
- 교사가 GitHub에 추가한 [재현용 소스](experiment_submit64.c)는 Day147 원격 소스에서 **record 선언 한 줄을 수정한 참고 파일**이다. 사용자가 로컬에서 직접 작성한 `challenge.c`의 바이트 완전 일치 여부는 미확인. 로컬 `challenge.c`가 이미 있을 수 있으므로 같은 이름으로 커밋하지 않았다.
- [재현용 빌드 스크립트](build_reproduction.sh)는 명령을 기록하기 위해 추가했으며, 사용자가 직접 실행했다는 증거는 없다.

## 1. 버퍼 크기 변경 후 최초 검증
사용자는 `record[64]`이라면 57바이트 입력은 버퍼 내부에 있으므로 정상 종료할 것으로 예상했다. 반면 `read` 최대 요청 크기 112는 여전히 64를 초과하므로 **취약점 자체는 해결되지 않는다**고 설명했다.

사용자가 `./archive_desk` 또는 GDB에서 전날 만든 57바이트 입력 파일을 사용한 결과, `received: 57`과 정상 종료를 보고했다. 대상 구분을 위해 파일을 복사한 뒤 처음 `./challenge.c`를 실행해 셸의 C 구문 오류가 났고, `run`을 셸에서 실행해 명령을 찾지 못한 상황을 **컴파일 실패와 실행 명령 혼동**으로 교정했다. `./archive_desk`는 셸에서, `run`은 GDB 안에서 사용한다.

## 2. 버퍼와 Canary 위치 — 불필요한 디버깅 단계 제거
처음 `b read`는 Submit이 아닌 `fgets` 내부의 `__GI___libc_read(fd=0,nbytes=1)`에서 중단됐다. 사용자가 백트레이스를 제출한 뒤 `$rdx==0x70` 조건으로 Submit 경로를 구분해 아래 레지스터를 제출했다:

```text
rdi 0x0
rsi 0x7fffffffdf10
rdx 0x70
bt: #0 __GI___libc_read
    #1 0x5555555552c2
    #2 0x5555555553cf
    #3 0x5555555554fe
```

하지만 사용자는 **전체 함수 역어셈블에서 버퍼 포인터를 만드는 명령과 Canary 저장 위치를 확인하면, 호출 프레임을 여러 번 이동하며 계산할 필요가 없다**고 지적했다. 이후 실제 변경 바이너리에서 사용자가 추적·보고한 주소 관계:

```text
record 시작 rbp-0x50  (64B)
padding            (8B)
Canary     rbp-0x8   (8B)
```

Canary 시작까지 거리: `0x50 - 0x8 = 0x48 = 72`바이트. **73번째 입력 바이트**가 Canary의 최하위 주소 바이트에 도달한다고 예측했다. 이 위치 관계는 사용자의 어셈블리 보고에 근거하며 이번 대화에 전체 disassembly 원문은 없었다.

## 3. 같은 길이 73B, 마지막 바이트만 다른 입력
입력 파일은 사용자 로컬에서 교사가 제공한 명령으로 생성했다:

```python
from pathlib import Path
Path("/tmp/day150_null.bin").write_bytes(b"2\n" + b"A"*72 + b"\x00")
Path("/tmp/day150_A.bin").write_bytes(b"2\n" + b"A"*73)
```

두 파일 모두 앞에 메뉴 선택 `2\n`, 뒤에 **Submit 입력 73B**가 있다. 사용자가 실제 제출한 출력:

```text
$ ./archive_desk < /tmp/day150_null.bin
Archive desk / local exercise
1 preview / 2 submit / 3 quit
> record> received: 73
1 preview / 2 submit / 3 quit
>

$ ./archive_desk < /tmp/day150_A.bin
Archive desk / local exercise
1 preview / 2 submit / 3 quit
> record> received: 73
*** stack smashing detected ***: terminated
Aborted (core dumped)
```

동일 길이에서도 첫 Canary 바이트를 `0x00`으로 덮으면 원래 값과 같을 것으로 예상해 검사를 통과하고, `0x41`로 덮으면 Canary 값 불일치로 실패하는 결과와 부합한다. **두 경우 모두 `record[64]` 바깥으로 9바이트가 기록된다.** 정상 종료와 메모리 안전성은 동일한 판단 기준이 아니다. 새 바이너리의 첫 Canary 바이트 GDB 덤프는 제출되지 않았으므로 세부 바이트 대조를 실제로 했다고 주장하지 않는다.

## 4. CS: 구조체 정렬, 내부·끝 Padding
문제:

```c
struct Packet {
    uint8_t type;
    uint32_t length;
    uint8_t flags;
};
```

사용자는 처음에 모른다고 답했지만, 교사의 4바이트 정렬 설명 후 `flags`가 offset8, `sizeof=12`, 끝 padding3B임을 스스로 계산했다. 일반적인 x86-64 GCC ABI의 레이아웃:

| 위치 | 필드 | 길이 |
| --- | --- | --- |
| offset 0 | type | 1B |
| offset 1..3 | 내부 padding | 3B |
| offset 4..7 | length | 4B |
| offset 8 | flags | 1B |
| offset 9..11 | trailing padding | 3B |

사용자 로컬에서 코드 컴파일·실행 후 제공한 결과:
```text
./packet_layout
sizeof: 12
type:   0
length: 4
flags:  8
```
참고용 [packet_layout_reference.c](packet_layout_reference.c)는 교사가 제시했던 코드의 재구성본이다. 기존 로컬의 `packet_layout.c` 내용을 원격에서 직접 읽어 동일성까지 확인한 것은 아니다.

## 5. 보안 2회독: Day118 AFL++ crash dedup
[과거 Day118 write-up](../Day118/write_up.txt)에서는 동일 크래시 주소만으로 동일 취약점이라 단정하지 않고 ASan 오류 종류·손상 객체·누락된 검사·재현 여부를 대조했다.

사용자가 먼저 **서로 다른 입력이 같은 명령어에서 크래시를 낸다면 같은 취약점일 가능성은 있으나 한 취약점이라는 단정은 비약**이라고 지적했다. 조건 변경 예제는 다음 코드의 `memcpy`에서 발생한 세 크래시다:

```c
char payload[16];
memcpy(payload, input, len);
```

| 입력 | len | input_size | 관찰을 가정한 오류 | 구분 |
| --- | ---: | ---: | --- | --- |
| A | 20 | 32 | stack-buffer-overflow WRITE | 목적지 16B를 4B 초과 |
| B | 8 | 4 | heap-buffer-overflow READ | 원본 4B를 4B 초과 |
| C | 24 | 32 | stack-buffer-overflow WRITE | 목적지 16B를 8B 초과 |

사용자는 `A/C`는 payload 크기를 넘어 쓰는 문제, `B`는 input보다 `len`이 커 범위 밖 읽기라고 스스로 설명했다. 이 가정된 예제에서는 **서로 다른 두 원인**(목적지 크기 검사 부재 / 원본 유효 길이 검사 부재)으로 분류하는 것이 타당하다. 세 입력이 발견됐으므로 세 취약점이라는 뜻은 아니며, 한 줄의 `memcpy`에서 발생했더라도 하나로 단정하지 않는다. 이 복습은 **손 추적**, 실제 ASan 신규 실행은 아니다.

## 2026-11-12 필수 보완 — 제어 가능/불가능/악용 전제 분리
기존 2026-11-11 로컬 실행 기록에서 추가 설명으로 검증한 **정적 조건 분석**이다. 이 보완에서는 새로운 반환 주소 덮어쓰기나 실행 흐름 탈취를 재현하지 않았다.

**사용자 최초 독립 판단**
- "입력버퍼 이상으로 입력을 넣을 수 있는 게 확인되었으므로 Canary, PIE Base, libc Base 등을 leak할 수 있다면 return address를 원하는 주소로 덮을 가능성이 있다."
- 입력 쓰기 시작 위치는 사용자가 자유롭게 고르는 게 아니고, 메모리의 쓰기 권한도 제약이 있다는 점을 설명했다.
- 추가 정보로 Canary/PIE/libc 주소와 실행 가능한 목표 주소, 방어 기법의 우회 여부를 들었다.
- 새 반례에서 `record` 시작 `rbp-0x50`에서 saved RIP `rbp+0x8`까지의 거리는 **`0x58`=88B**라고 정확히 계산했다.
- "원본 Canary 값을 정확히 모르며 다른 전제들도 확인되지 않았다"고 답해 현재는 실행 흐름 탈취 성공을 주장할 수 없다고 설명했다.

**명확한 분리**
| 종류 | 이번 기록에서 근거/한계 |
| --- | --- |
| 제어 가능 | 입력 내용, 프로그램에 전달하는 바이트 수와 첫 저장 바이트의 내용, `record` 이후 연속적인 위치에 기록되는 입력 바이트. 73B에서 끝 바이트가 00 vs 41일 때 탐지 결과 변화는 실제로 관찰함. |
| 제어 불가능/직접 지정 불가 | `receive_bytes(record,112)`의 목적지 **시작 포인터는 코드에서 정해짐**; 호출자가 임의 주소를 지정하는 arbitrary write가 아님. 저장된 Canary의 **원본 값**, PIE/libc 매핑 베이스, 메모리 페이지 권한은 입력값 하나로 자유롭게 선택할 수 없음. `read`의 실제 반환 길이는 전달한 파일과 입출력 환경에 따라 달라질 수 있고, 112는 상한임. |
| 악용 전제/미검증 | 실제 saved RIP까지 89B 이상이 한 번에 전달되고 반영되는지 검증하지 않았음. 버퍼 시작+88B가 saved RIP **시작 주소**이므로 89번째 바이트가 saved RIP 첫 바이트에 닿으며 8B 전부를 덮는다면 96B가 필요(호출 read 최대112B 요청과 별개). 그 사이의 Canary 8B를 적절히 보존/통과해야 함. 목적지 주소가 실행 가능한 합당한 제어 이전 대상인지, ASLR에서 필요한 매핑 기준값/오프셋을 알고 있는지, 이후 ABI/스택 정렬 및 다른 보호기법을 충족하는지 별도 확인 필요. |
| 이미 검증 | 57B/73B 길이 변화 및 Canary 검출 여부, 현재 사용자의 보고에 따른 rbp 상대 오프셋, read 요청 상한112. |
| 미검증 | Canary 전체 누출·우회, saved RIP 직접 덤프·원하는 값으로 변경한 증거, 실제 ret에 의한 흐름 변경, ROP/쉘 취득. |

**정밀 교정:** 정보누출(leak)로 현재 값을 **알아내는 것**과 값 자체를 **제어하는 것**은 다르다. 또한 Canary/PIE/libc Base가 항상 모두 필요한 것은 아니고, 사용하려는 제어 이전 경로에 따라 필요한 정보가 달라진다. 현재까지는 **연속된 스택 OOB Write가 증명**된 것이며 임의 주소 쓰기·실행 흐름 탈취는 가능성/전제 단계다.

**보완 판정:** Day150 메인 누락 과제였던 제어 가능·불가능·악용 전제 구분과 반례 주소 계산을 사용자 설명으로 확인하여 완료. 교사의 분류 설명과 후속 질문, 사용자의 `0x58` 답변 및 Canary 값 미확인 인지를 구분해 기록. **새 실습·익스플로잇 성공으로 간주하지 않음.**



## 2026-11-12 필수 보완 — CS 정수형 축소로 인한 검사 우회 실측

**계획표 요구:** Day150 CS에서 정수 변환·배열의 **조건 변경 실험과 반론 검증**. 기존 2026-11-11 `struct Packet` 레이아웃 실험은 별도 성과로 인정하지만 이 필수 항목을 대체하지 않는다.

이번에는 앞서 Day149에서 검증한 입력 길이 검사를 **먼저 `uint8_t`로 축소한 뒤 검사**하면 어떻게 되는지 비교했다. 교사가 작성한 `wrong_check(size_t input_size,int32_t len)`와 `right_check(...)`는 실제 메모리 복사를 실행하지 않고 허용 여부를 반환한다. [참고 C 소스](narrowing_lab_reference.c)는 교사가 대화에서 제시한 코드의 복원이며 사용자가 로컬에서 만든 `narrowing_lab.c` 원본과 byte 단위 동일함은 확인하지 못했다.

**사용자가 실행 전 독립 예측한 핵심:** `uint8_t`는 0~255로 값의 범위가 제한되므로 `(uint8_t)256==0`; `wrong_check`에서 허용을 의미하는 0으로 잘못 판정할 수 있다.

**로컬 GCC 실측(사용자 제공):**
```text
A: wrong=0 right=0
B: wrong=0 right=-3
C: wrong=-4 right=-3
```
사용자는 세 결과가 예상과 일치했다고 밝혔다. 로컬 실행 명령은 `gcc -std=c11 -O0 -Wall -Wextra narrowing_lab.c -o narrowing_lab; ./narrowing_lab`로 안내했으나 원본 빌드 로그/환경 버전은 제출되지 않았다.

| 조건 | 축소/원래 값 | wrong_check | right_check | 원인 및 의미 |
| --- | --- | --- | --- | --- |
| A: `input_size=12,len=8` | `n=8` | 0 | 0 | 본문 크기 8B와 목적지 한도 8B의 정확한 경계 허용 |
| B: `input_size=12,len=256` | `n=0` | 0 | -3 | `uint8_t` 축소로 유효 길이 검사가 원래의 256을 잃어버림. 원래 길이 256은 헤더4 제외 본문8을 초과. 축소 검사가 잘못 허용 |
| C: `input_size=12,len=9` | `n=9` | -4 | -3 | 둘 다 거부하지만 검사의 우선순위가 달라 다른 오류 코드가 나옴: wrong에서는 목적지 한도8 검사 먼저, right에서는 원본 길이8 검사 먼저 |

**반론:** "어차피 프로그램이 실행하는 `memcpy`가 없으니 실제 오버플로우를 증명했다"는 주장은 틀림. 이번 실험으로 입증된 것은 **입력 길이 검사가 잘못 허용하는 조건**이며 실제 OOB Read/Write의 재현은 아님. 사용자 원문은 축소가 0으로 되는 점과 B에서 검사 통과·세 결과 일치를 설명했고, 이 반론은 교사의 분석으로 별도 표시한다.

**수정 원리:** 데이터 축소 전의 원래 `len` 값을 기준으로 음수와 원본 데이터 길이, 목적지 한도를 검사한다. 축소된 값을 원래 길이의 검증 기준으로 쓰지 않는다. 축소가 불가피하다면 먼저 축소 전 표현 가능 범위를 검사한다.

**보완 판정:** Day150 CS 누락 항목의 조건 변경과 로컬 실행을 확인하여 완료. 사용자의 결과·추론과 교사의 주석·반론 해설을 구분하며, 새 ASan/OOB 오류 실행은 없었다.



## 2026-11-12 필수 보완 — 이전 Day082 Fake Stack Pivot 복습

**기준 자료:** [Day082 write_up.txt](../../Day040-100/Day082/write_up.txt). 원본 기록에 따르면 `malloc` 청크의 시작 주소를 Fake Stack으로 사용한 첫 시도가 실패했고 `ret` 가젯을 제거한 재시도도 실패. 실패 원인을 스택이 낮은 주소로 확장할 때 객체 시작 전 주소에 접근하는 것으로 식별하고, `region` 0x5000B를 확보해 Fake Stack/obj를 `region + 0x4000`으로 옮긴 다음 성공했다고 기록함.

**사용자 회상 및 직접 반례 답변 (2026-11-12):**
- 원래 실패 원인을 첫 질문에서는 기억하지 못함(`"기억이 안낭"`). 정렬 문제만은 아닌 것 같다고 답함.
- 3번째 질문에서 스스로 `RSP`가 함수 실행 중 낮은 주소 쪽으로 움직일 수 있으므로 `region` 시작점에 피벗하면 그 아래의 의도하지 않은 메모리를 건드릴 수 있다며, `region+0x4000`으로 이동시켜 아래쪽 여유 공간을 확보한 이유를 정확하게 재구성함.
- 교사는 변경 반례로 `region` 시작 `0x10000`, 크기 `0x5000`, 피벗 후 `rsp=0x10010`, `sub rsp,0x80`을 제시함.
- 사용자 독립 반례 설명: `rsp`가 `0x10010`에서 `0x80`만큼 내려가 `region` 시작보다 아래로 벗어나므로 접근 문제가 발생할 수 있다고 판단. 수치 계산 `0x10010-0x80=0xFF90`이며 `0x10000`보다 `0x70` 아래임.
- **엄밀한 보충:** `sub rsp,0x80` 자체는 주소 계산/레지스터 변경이지 해당 메모리에 쓰는 동작이 아니다. **그 이후** 해당 주소에 push/call 또는 지역 스택 쓰기처럼 실제 접근할 경우 영역 밖 접근 문제가 생긴다. 할당 영역 밖 주소가 운 좋게 매핑되어 있으면 곧바로 SIGSEGV가 나지 않을 수도 있지만, 할당 객체의 유효한 영역이 아니라 안전하다고 결론 내릴 수 없음.
