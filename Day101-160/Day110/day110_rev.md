# Day110 - Reversing Portfolio Checkpoint

## 점검 목적

Day090부터 Day109까지 작성한 리버싱 문서 중 서로 다른 분석 역량을 보여주는 8개를 선정했다. 각 문서가 직접 증거, 추론, 결론, 재현 명령과 실패 사례를 포함하는지 점검했다.

## 품질 판단

8개 문서 모두 분석 주제의 핵심 결론과 판단 근거를 포함한다. 특히 함수 XREF, ABI 인자, 간접 호출 대상, anti-debug 반환값, stack offset과 caller 도달 가능성을 이용해 Ghidra의 추론을 어셈블리 또는 GDB 결과와 연결했다.

다만 과거 문서들은 분석 결과는 기록했지만 정확한 실행 명령과 저장소 상대 경로가 자주 누락됐다. 이후 문서에서는 다음 구조를 기본 형식으로 사용한다.

```text
분석 대상과 해시
→ 직접 증거
→ 추론 과정
→ 결론
→ 재현 명령
→ 실패 케이스
→ 분석의 한계
```

## 저장소 문제

일부 Day 폴더에는 내용이 채워진 `write_up.txt`와 비어 있는 `day*_rev.md` 양식이 함께 존재한다. 포트폴리오 README에서는 빈 양식을 제외하고 실제 분석 내용이 있는 문서만 연결한다. 기존 파일을 모두 다시 작성하거나 이름을 일괄 변경하지 않고, 이후 문서부터 `.md` 형식으로 통일한다.

## 수정 범위

* Day109 문서를 `day109_rev.md`로 정리하고 분석 대상 경로, 재현 명령과 Canary 실패 사례를 추가했다.
* Day100의 깨진 Markdown 코드 블록만 수정한다.
* 나머지 과거 문서는 원래 분석 기록을 보존하고 부족한 항목을 이 점검 문서에 기록한다.
* 저장소 README에 위 8개 문서의 링크와 한 줄 요약을 추가한다.

## 한계

이번 점검에서는 모든 과거 바이너리를 다시 실행하지 않았다. 기존 문서와 진행 로그에 기록된 GDB·objdump 검증 결과를 기준으로 평가했으며, Day109의 56/57바이트 Canary 경계만 다시 실행해 확인했다.

## 결론

좋은 리버싱 문서는 최종 입력이나 성공 화면만 보여주는 문서가 아니다. 관찰한 명령과 값, 그 증거에서 도출한 추론, 확정할 수 없는 한계가 분리되어야 다른 분석자가 같은 결론을 재현할 수 있다.
