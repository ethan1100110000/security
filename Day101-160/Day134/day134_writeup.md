## 1. 메인: 복사 함수의 성공과 거부를 어떻게 검증하는가

```c
int copy_data(char *dst, size_t capacity,
              const char *src, size_t src_size,
              size_t length)
{
    if (length > src_size) return 1;
    if (length > capacity) return 2;
    memcpy(dst, src, length);
    return 0;
}
```

원본과 목적지는 살아 있는 비중첩 객체이며 원본은 읽기, 목적지는 쓰기가 가능하도록 테스트에서 준비했다. src_size는 실제 준비한 원본 크기이고 목적지는 16바이트 배열이다. 호출자가 전달하는 길이·용량이 정확하다는 전제도 필요하다.

사용자는 정상 복사 확인에서 복사된 내용이 원본과 같은지 확인해야 한다고 답했다. 크기만 같아서는 정확한 복사 여부를 알 수 없다. 중간 NUL이 있는 바이너리는 strcmp 대신 memcmp로 지정한 length바이트를 비교해야 한다고 설명했다.

### 검증 기준
- 각 사례 실행 전에 목적지 전체를 0xAA로 초기화한다.
- 성공: 기대 반환값 0, 처음 length바이트가 src와 일치, 목적지의 나머지 바이트가 0xAA로 유지되는지 확인한다.
- 거부: 원본 초과는 1, 목적지 초과는 2를 기대하며 목적지 전체가 0xAA로 유지되는지 확인한다.
- 반환값은 함수 결과다. 테스트 프로그램 자체의 종료 코드는 전체 사례 통과 시 0이다.

사용자는 성공 시 앞 4바이트는 원본, 뒤 12바이트는 0xAA라고 예상했다. 거부 후 목적지가 유지되어야 한다고도 답했다. 이후 두 확인 목적을 섞어 설명하여, 성공 시 미복사 영역 유지와 거부 시 전체 무변경을 구분했다. 오류 반환 전에 일부 쓰기가 있었다면 실패라고 답했다.

## 2. 실제 경계 테스트 결과

| 사례 | src_size | capacity | length | 함수 반환 | 내용 확인 | 변경 금지 영역 |
|---|---:|---:|---:|---:|---|---|
| 원본 길이와 동일 | 4 | 16 | 4 | 0 | 처음 4바이트 일치 | 뒤 12바이트 유지 |
| 원본 1바이트 초과 | 4 | 16 | 5 | 1 | 거부로 해당 없음 | 전체 16바이트 유지 |
| 목적지 용량과 동일 | 32 | 16 | 16 | 0 | 16바이트 일치 | 남은 영역 0바이트 |
| 목적지 1바이트 초과 | 32 | 16 | 17 | 2 | 거부로 해당 없음 | 전체 16바이트 유지 |
| 중간 NUL 포함 | 4 | 16 | 4 | 0 | 41 00 42 43 일치 | 뒤 12바이트 유지 |

최종 소스 기준 5/5 통과, 컴파일 종료 코드 0, 실행 종료 코드 0이다. 목적지 길이와 정확히 같은 사례는 목적지 내부의 남은 영역이 없으므로, 변경 금지 영역 검사는 길이 0인 비교다. 배열 바깥에 별도 canary를 두어 관찰한 것은 아니다.

중간 NUL 사례의 실제 출력:
```text
41 00 42 43 AA AA AA AA AA AA AA AA AA AA AA AA
```

준비 단계에서 NUL 사례는 처음 41 00 43 44로 생성되어 통과했다. 대화에서 합의한 41 00 42 43과 일치시키도록 테스트 원본을 명시 배열로 바꾼 뒤 다시 빌드·실행했다. results.txt와 sha256.txt는 이 최종 소스·최종 실행에 대응한다.

### 한계
목적지의 실행 후 내용 유지는 관찰한 범위의 최종 상태다. 일시적으로 쓰고 되돌렸을 가능성까지 이 비교만으로 배제하지는 않는다. 반환 전 memcpy가 없다는 소스와 역어셈블 근거를 함께 읽는다. 다섯 사례의 통과는 모든 입력이나 함수 전체의 메모리 안전성 증명이 아니다. 새 crash·sanitizer 보고서는 없다.

## 3. CS: 엔디언 예상과 실제 출력

사용자는 uint32_t 0x12345678의 리틀 엔디언 메모리 순서를 78 56 34 12로, 낮은 주소부터 01 02인 두 바이트의 리틀 엔디언 해석을 0x0201로 골랐다.

빅 엔디언 형식과 리틀 엔디언 파서의 불일치 질문에서는 막혀, 01 02를 빅 엔디언으로는 0x0102, 리틀 엔디언으로는 0x0201로 해석한다는 표 설명을 받았다. 조건 변경 입력 00 10을 잘못 리틀 엔디언으로 읽으면 0x1000이라고 답했다.

### endian_probe.c 실제 출력
```text
value=0x12345678
memory low-to-high: 78 56 34 12
input: 00 10
big-endian decode: 0x0010 (16)
little-endian decode: 0x1000 (4096)
```

컴파일과 실행은 모두 종료 코드 0이다. value의 메모리는 unsigned char 포인터로 객체 표현을 읽었다. 두 디코딩은 시프트와 OR로 해석 순서를 명시했으며 정렬되지 않은 uint16_t 포인터 역참조를 사용하지 않았다.

- 첫 바이트 출력은 이번 실행 환경이 리틀 엔디언임을 관찰한 것이다.
- 빅/리틀 디코딩 출력은 명시한 해석 코드의 결과이며 환경에 따라 자동으로 선택한 결과가 아니다.
- 입력 형식에 맞는 길이 해석과, 얻은 길이가 원본·목적지 범위에 드는지 검사는 둘 다 필요하다. 사용자는 둘 다 필요하다고 답했고 세부 이유는 교사가 보충했다.

## 4. 보안 2회독: 실행한 바이너리의 역어셈블

copy_test의 copy_data를 objdump -d -Mintel --disassemble=copy_data로 읽었다. 실제 GDB 단일 단계 실행이나 런타임 스택 주소 관찰은 하지 않았다.

### 프레임 생성
```asm
push rbp
mov  rbp, rsp
sub  rsp, 0x30
```

컴파일러는 이 빌드에서 호출자의 rbp를 보존하고 현재 프레임 기준을 만들었다. 함수 종료 후 다음 코드로 돌아가야 하기 때문이라는 사용자 설명은 call/ret의 역할과 구분했다. 최적화나 프레임 포인터 옵션에 따라 이 프레임 형태는 달라질 수 있다.

사용자는 sub rsp가 rbp를 함께 바꾸지 않는다고 답했고, rbp=0x1000일 때 rbp-8 주소를 계산했다. [rbp-8]은 주소 자체가 아니라 그 주소의 저장값을 나타낸다는 표기를 보충했다.

### 인자 저장 위치 — 이번 실제 빌드
| 인자 | 진입 레지스터 | 프레임 내 저장 위치 |
|---|---|---|
| dst | rdi | [rbp-0x8] |
| capacity | rsi | [rbp-0x10] |
| src | rdx | [rbp-0x18] |
| src_size | rcx | [rbp-0x20] |
| length | r8 | [rbp-0x28] |

이 위치는 이번 GCC 빌드에서 확인한 것이다. 이전 설명용 레지스터 배치나 다른 빌드에 동일하게 적용하지 않는다.

### 첫 검사
```asm
mov rax, QWORD PTR [rbp-0x28]
cmp QWORD PTR [rbp-0x20], rax
jae 125a
mov eax, 1
jmp 1287
```

cmp의 앞 피연산자는 src_size, 뒤는 length다. unsigned에서 src_size >= length면 jae로 거부 코드를 건너뛰고 다음 검사에 간다. 이전 length > capacity일 때 거부 쪽으로 점프하는 예제와 비교 순서·목적지가 다르다.

사용자는 jae 의미를 잊어 재설명을 받았고, 4/4이면 점프, 4/5이면 점프하지 않고 반환값 1이라고 답했다. 실행된 테스트의 원본 초과 사례 반환값 1과 정적 코드 경로가 일치했다. 정적 해석을 동적 분기 추적 결과라고 기록하지 않는다.

### 종료
```asm
leave
ret
```

이번 64비트 프레임에서 leave는 mov rsp, rbp; pop rbp에 해당한다. 이후 ret은 [rsp]의 복귀 주소를 rip에 넣어 돌아간다. 사용자는 ret이 복귀 주소를 읽는다고 답했다. saved rbp와 복귀 주소는 다르다.

## 5. 실행 재현

이 폴더에서 다음 순서로 실행한다.

```bash
cc -std=c11 -Wall -Wextra -Werror -O0 -g copy_test.c -o copy_test
./copy_test > results.txt
cc -std=c11 -Wall -Wextra -Werror -O0 -g endian_probe.c -o endian_probe
./endian_probe > endian_results.txt
objdump -d -Mintel --disassemble=copy_data copy_test > copy_data_disassembly.txt
```

각 명령의 종료 코드를 따로 확인한다. 환경이 다르면 역어셈블 주소나 프레임 배치는 달라질 수 있다. source와 결과를 보존하고 실행 파일은 재빌드한다. sha256.txt의 실행 파일 해시는 오늘 실행한 바이너리의 식별 기록이며 바이너리 자체는 커밋하지 않는다.
