# Day138 — 공통 거부 경로와 부분 레지스터 쓰기

- 학습일: 2026-10-20
- 계획: W03 바이너리 기초 / 3주차 2/5
- 상태: 오늘 메인·CS·보안 2회독 범위 종료
- 실제 학습 시간: 미측정
- 실제 실행: 교사 컨테이너에서 별도 어셈블리/C 레지스터 폭 실험
- 구분: copy_data의 제어 흐름은 Day137 실제 역어셈블을 읽은 정적 해석이며, GDB로 해당 함수의 레지스터를 관찰하지 않았다.

## 1. 메인: 공통 종료 경로와 오류 값 준비

대상은 Day137/disassembly_O2.txt에 보존한 실제 copy_data다. 이해를 위한 발췌에서 reject는 실제 공통 거부 위치 0x1318에 붙인 설명용 이름이다.

```asm
mov r9, rcx       ; 진입 rcx의 src_size 보관
mov ecx, 1       ; 원본 초과 오류 값 준비
cmp r9, r8       ; src_size와 length
jb  reject
mov ecx, 2       ; 목적지 초과 오류 값 준비
cmp rsi, r8      ; capacity와 length
jb  reject

; 정상 복사 경로와 별도 반환은 생략

reject:
mov eax, ecx
ret
```

두 jb는 같은 주소로 이동하지만, 도착 시 ecx가 어느 값을 갖는지는 진입 경로에 따라 다르다.
- 첫 비교에서 거부: ecx=1인 상태로 이동하여 1 반환.
- 첫 비교 통과 후 두 번째에서 거부: ecx=2인 상태로 이동하여 2 반환.
- 정상 경로는 이 거부 위치로 흘러가는 것이 아니라 복사 후 별도로 0을 반환한다.

사용자는 각 비교 전에 ecx에 1/2를 넣고 공통 위치에서 사용하므로 결과를 구분할 수 있다고 직접 설명했다.

### src_size를 먼저 옮기는 이유
함수 진입 시 rcx=src_size지만, 이후 ecx를 오류 값으로 쓰면 rcx도 바뀐다. 따라서 mov r9,rcx로 원래 src_size를 보관한 뒤 cmp r9,r8로 비교한다.

사용자는 rcx 값을 r9에 먼저 복사하는 목적을 맞혔다. ecx를 하위 “4비트”라고 표현한 것은 하위 32비트=4바이트로 교정했다. r9는 별도 레지스터이므로 뒤의 ecx 쓰기로 자동 변경되지 않는다.

### 경로 추적
src_size=32, capacity=16, length=17:
1. r9=32를 보관하고 ecx=1 준비.
2. 32<17은 거짓이므로 첫 jb는 이동하지 않음.
3. ecx=2로 변경.
4. 16<17은 참이므로 공통 reject로 이동.
5. eax=ecx=2를 반환.

사용자는 두 번째 capacity/length 비교에서 점프하고 반환값은 2라고 답했다. 이 입력 경로를 오늘 GDB로 실행 추적한 것은 아니다.

## 2. CS: 32비트 쓰기와 16비트 쓰기의 차이

x86-64의 이번 명령에서:
- ecx는 rcx 하위 32비트다. ecx에 쓰면 상위 32비트는 0이 된다.
- cx는 rcx 하위 16비트다. cx에 쓰면 나머지 상위 48비트는 유지된다.

초기값을 매번 0x1122334455667788로 되돌린 뒤 각각 수행한다.

| 명령 | 예상 rcx | 실제 결과 |
|---|---|---|
| mov ecx,1 | 0x0000000000000001 | 일치 |
| mov cx,1 | 0x1122334455660001 | 일치 |

사용자는 첫 결과를 맞혔지만 cx 쓰기도 같을 것이라고 예상했다. 마지막 네 자리만 바꾸는 차이를 설명받았다.

### 2진수와 16진수 표기 교정
mov cx,2 조건 변경에서 사용자는 0x1122334455660010이라고 답했다. 이는 진법 혼동이었다.
- 십진수 2 = 이진수 0b0010 = 16진수 0x0002.
- 따라서 같은 초기값에서 mov cx,2의 예상 rcx는 0x1122334455660002.
- 0x0010은 십진수 16이지 2가 아니다.

사용자는 이후 “0010, 0002”로 두 진법 표현을 구분했다. cx=2 사례는 문답 예상이고, 오늘 실제 실행한 것은 각각 ecx=1과 cx=1 두 사례다.

## 3. 실제 레지스터 폭 실험

파일:
- register_width.S: 각 함수가 rcx 초기값 설정 → ecx 또는 cx에 1 쓰기 → rcx를 rax로 복사해 반환.
- register_width_test.c: 두 함수를 호출하여 64비트 반환값을 출력하고 기대값과 비교.
- register_width_results.txt: 실제 출력.
- environment.txt, sha256.txt: 환경과 파일 식별 기록.

소스의 어셈블리는 GNU AT&T 문법이므로 피연산자 순서가 대화의 Intel 문법과 다르다. 예를 들어 mov $1,%ecx는 Intel의 mov ecx,1에 대응한다.

```bash
cc -std=c11 -Wall -Wextra -Werror -O0 -g register_width_test.c register_width.S -o register_width_test
./register_width_test > register_width_results.txt
```

각 명령 종료 코드를 확인한다. 빌드와 실행 모두 0이며 두 기대값 검사는 PASS다.

```text
initial rcx = 0x1122334455667788 (reset before each case)
mov ecx, 1 -> rcx = 0x0000000000000001 expected=0x0000000000000001 PASS
mov cx, 1  -> rcx = 0x1122334455660001 expected=0x1122334455660001 PASS
```

출력은 실행한 어셈블리가 rcx 값을 rax로 옮겨 반환한 관찰이다. GDB로 해당 순간을 정지해서 캡처한 레지스터 덤프는 아니다. 사용자 WSL의 실행 결과도 아니다. 바이너리는 재빌드하며 커밋에는 소스·원자료·해시를 보존한다.

## 4. 보안 2회독: 실험 대상과 직접 관찰의 범위

사용자는 오늘 폭 실험으로 기존 copy_data 내부의 r9 저장 순간을 직접 관찰한 것은 아니라고 예상했다.
- 직접 실행한 대상: 별도 레지스터 폭 실험 함수.
- 정적으로 읽은 대상: 기존 O2 copy_data의 mov r9,rcx와 분기.
- 아직 하지 않은 것: 기존 copy_data에서 GDB 단일 단계로 전후 rcx/r9 값을 확인하기.

직접 확인할 방법을 묻자 사용자는 r9의 변화 관찰을 제안했다. 교사는 원본인 실행 전 rcx와 실행 후 r9를 함께 비교해야 원하는 값을 복사했는지 판단할 수 있다고 보완했다.

실행 전 rcx=32라고 가정한 손 추적:
| 시점 | rcx | r9 |
|---|---:|---:|
| mov r9,rcx 직후 | 32 | 32 |
| 이어 mov ecx,1 직후 | 1 | 32 |

마지막 상태를 사용자가 독립적으로 맞혔다. 위 표는 확인 방법과 예상값이며 실제 GDB 관찰 결과가 아니다.

- CS: ecx/cx 폭과 상위 비트 처리, 비트/바이트 및 진법 혼동 교정. 실제 두 사례 실행.
