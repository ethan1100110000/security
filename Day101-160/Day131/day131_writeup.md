## 1. 메인: TPAR와 TinyXML-2 비교

| 항목 | TPAR | TinyXML-2 |
|---|---|---|
| 입력 형식 | 매직·Version·Command·Length·Payload로 구성된 자체 바이너리 형식 | 태그·속성·텍스트·중첩 등을 가진 XML |
| 구현 언어 | C | C++ |
| 하네스의 공통 역할 | 입력을 읽어 시작 주소와 실제 읽은 길이를 파서에 전달 | 입력을 읽어 시작 주소와 실제 읽은 길이를 Parse에 전달 |
| 오류 구분 | 형식 오류 거부와 메모리 오류를 구분 | XML 문법 오류 반환과 crash를 구분 |

사용자는 처음 차이를 “XML이냐 C냐”로 표현했다. XML은 입력 형식, C/C++는 구현 언어로 서로 다른 비교 축임을 교정했다. 닫는 태그 불일치에 따른 정상 오류 반환은 crash가 아니라 입력 형식 오류 처리라고 설명했다.

## 2. TPAR 입력·처리·출력과 수정 원리

입력 바이트를 읽은 하네스는 input의 시작 주소와 실제 입력 길이 input_size를 파서에 전달한다. TPAR 헤더는 7바이트이며 헤더의 length는 payload로 복사할 데이터 길이를 나타낸다. 헤더 최소 길이와 형식을 확인하고 원본 데이터가 충분한지, 목적지 공간이 충분한지 검사한 뒤 복사한다. command 1의 출력은 지정한 바이트 수를 사용하는 fwrite로 수행한다.

| 조건 | 확인 목적 | 기존 사례 |
|---|---|---|
| input_size >= 7 | 헤더 접근이 실제 입력 범위 안인지 확인 | 나머지 길이 계산 전에 필요 |
| length <= input_size - 7 | 복사할 원본 데이터가 충분한지 확인 | 기존에 존재 |
| length <= sizeof(payload) | 목적지 배열에 복사할 공간이 충분한지 확인 | 누락된 검사, 수정으로 추가 |

기존 문제는 입력 길이 검사가 전부 없었던 것이 아니라 목적지 payload 배열의 용량 검사가 빠진 것이었다. 원본 길이 검사를 통과해도 목적지 용량보다 큰 length를 memcpy에 전달하면 범위 밖 쓰기가 발생할 수 있다. 수정은 복사 전에 length > sizeof(payload)를 거부하는 방식이다. sizeof로 전체 용량을 얻는 것은 해당 위치의 payload가 배열일 때다.

사용자는 입력·하네스·두 범위 검사·수정 이유를 한 문단으로 설명했고, 읽기 범위와 쓰기 범위를 구분했다. “input - 7” 표기는 “input_size - 7”로 교정했다. 포인터 주소의 뺄셈과 입력 길이 계산은 다르다.

### 검증 이력과 한계
- 기존 Day119~120 기록에는 초과 길이 거부와 경계·기존 PoC 검증 이력이 있다.
- 최근 Day130 write-up에 정리된 length=4 정상 입력 두 건은 정상 출력 및 중간 NUL 처리에 관한 확인이다. 그 두 실행 자체에서는 초과 길이 거부 분기를 실행하지 않았다.
- 오늘은 그 기록을 설명했으며 거부 분기를 새로 실행하지 않았다.
- 특정 경계와 PoC에 대한 결과를 모든 입력의 안전성으로 일반화하지 않는다.

## 3. 대표 과제 후보: 상태와 실행 비용

### 후보 1
질문: 이전 입력을 처리한 상태가 다음 입력의 파싱 결과에 영향을 주는가?

같은 객체에서 A 다음에 B를 처리한 결과와 새 객체에서 B만 처리한 결과를 비교한다. 사용자는 독립적으로 B를 넣었을 때와 비교해야 한다고 답했다. 재사용 시 이전 결과가 실제 남는지는 초기화 구현과 관찰로 확인할 사항이며, TinyXML-2의 상태 누수를 발견했다고 기록하지 않는다.

### 후보 2
질문: 요구한 처리 결과를 보장할 때, 매번 새 객체를 생성하는 방식과 기존 객체를 초기화·재사용하는 방식의 실행 비용은 어떻게 다른가?

빌드 옵션, 실행 환경, 입력 내용·순서, 반복 횟수와 측정 범위를 맞춰 비교한다. “새 파일 생성”은 “새 XMLDocument 객체 생성”으로 교정했다. 실제 비교 실험은 아직 수행하지 않았다.

### 정확성 판정
속도 비교 전에 성공·오류 반환값과 파싱된 태그·속성·텍스트·구조가 각 입력의 기대 결과에 맞는지 확인한다. 예시 입력 user의 role 속성이 한쪽 결과에서 빠지면 양쪽 반환값이 성공이어도 같은 처리를 했다고 볼 수 없다.

사용자는 처음 “누락의 영향이 작으면 빠른 방식을 선택”한다고 답했다. 필수 파싱 내용 누락은 정확성 실패이고, 정확한 처리 결과를 내는 조건끼리 비용을 비교해야 함을 교정했다. 이후 속성 누락은 같은 결과가 아니며 정확성 조건을 통과하지 못한다고 답했다. 두 방식끼리의 일치만으로 기준 결과 자체의 정확성이 자동 증명되는 것은 아니다.

## 4. CS: 포인터·값·용량·객체 수명

### 포인터 크기와 버퍼 용량
포인터 인자 payload의 sizeof는 포인터 변수 자체의 크기이지 가리키는 배열의 용량이 아니다. 이전 확인 환경에서는 8바이트였으며 모든 환경에 동일하다고 일반화하지 않는다. 복사 목적지를 포인터로 받는 함수는 capacity를 별도로 받아 length와 비교해야 한다.

길이가 용량 이하여도 이미 free된 객체에 접근하면 안 된다. 객체 수명이 끝났으므로 쓰기는 use-after-free에 해당한다. 사용자는 객체 수명 종료 이후 접근 금지라는 이유를 설명했다. 해제 영역의 할당기 관리 정보나 주소 누출 가능성은 별도 조건이 필요한 이야기다.

### 작은 코드의 손 추적
호출자에서 int x = 10; int *q = &x;를 준비하고 update(q)를 호출한다고 가정했다.

| update 내부 동작 | 함수 내부 변화 | 반환 후 호출자 상태 |
|---|---|---|
| *p = 20 | p가 가리키는 x 값을 변경 | x=20, q는 x를 가리킴 |
| int y=20; p=&y; | 지역 포인터 p의 주소값만 변경 | x=10, q는 x를 가리킴 |
| int y=20; p=&y; *p=30; | p를 통해 y 값 변경 | x=10, q는 x를 가리킴. y는 수명 종료 |

p와 q는 같은 주소값을 가질 수 있어도 서로 다른 포인터 변수다. 함수 인자에는 q의 주소값이 복사된다. *p에 대입하면 대상 값을 바꾸고 p에 대입하면 지역 포인터의 주소값을 바꾼다.

사용자는 처음 p=&y가 q의 대상도 y로 바꾼다고 답했다. 값 전달과 별도 포인터 변수라는 점을 교정한 뒤, *p는 대상 값 변경, p는 저장된 주소 변경이라고 구분했고 조건 변경 예제에서 x=10, y=30을 맞혔다. 이는 코드 추적 답변이며 실제 실행 출력이 아니다.

## 5. 보안 전반 2회독

| 주제 | 질문과 사용자 답변 | 확인한 원리 |
|---|---|---|
| 파일 권한 | 입력 파일에 실행 권한은 불필요. 하네스를 실행하므로 | 데이터 파일은 읽기, 실행 파일은 실행이라는 역할 구분 |
| 컴파일·GDB | 재빌드하지 않으면 수정 검사는 미적용. GDB는 컴파일된 대상 실행 | 소스 수정과 실행 파일 변경은 별개 |
| 별도 프로세스 | 공유 메모리 없는 두 프로세스의 counter는 함께 바뀌지 않음 | 별도 주소 공간과 자기 변수 저장소 |
| persistent 반복 | 같은 프로세스의 반복문 밖 counter는 필요 시 직접 초기화 | 다음 입력 처리 시작이 일반 상태를 자동 초기화하지 않음 |

마지막 답변에서 사용자는 반복문 밖 변수는 따로 초기화해야 한다고 설명했다. 이 원리를 메인의 상태 초기화 과제와 연결했다. 이번 복습은 대화 회상과 피드백으로 수행했으며 새 관찰 로그를 만들지 않았다.
