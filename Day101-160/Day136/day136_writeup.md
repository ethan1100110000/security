## 1. 메인: 확인한 범위와 한계

교사는 처음 기존 copy_data의 두 범위 검사와 권한·수명 사례를 다시 종합 질문했다. 사용자가 이미 했던 내용임을 지적해, 기존 답변을 근거로 인정하고 개별 기초 질문의 반복은 중단했다.

Day134~135에서 정상·경계·중간 NUL·중첩 오류·선행 쓰기 검출을 확인했지만 모든 입력의 안전성을 증명한 것은 아니다. 사용자는 아직 모든 입력을 확인한 것은 아니라고 답했다.

이번 추가 사례는 살아 있는 읽기 가능한 원본 4바이트와 쓰기 가능한 목적지 16바이트에 대해 length=0이다. 목적지는 모두 AA로 초기화했다.

```c
if (length > src_size) return 1;
if (length > capacity) return 2;
memcpy(dst, src, length);
return 0;
```

사용자는 목적지가 AA 그대로일 것이라고 예상했다. 교사는 두 조건을 통과해 함수 반환값 0이라는 점을 보충했다. 성공했지만 0바이트를 복사한 상태와 거부로 인해 목적지가 유지되는 상태는 반환값·제어 흐름이 다르다.

### 실제 결과
```text
src_size=4 capacity=16 length=0 rc=0 expected_rc=0 unchanged=PASS dst=AA AA AA AA AA AA AA AA AA AA AA AA AA AA AA AA
```

C11, Wall/Wextra/Werror, O0, g 조건의 빌드와 실행 모두 종료 코드 0이다. zero_length_test.c와 zero_length_results.txt를 보존한다. NULL 포인터를 0길이로 전달하는 사례를 시험한 것은 아니다. sanitizer·퍼징·새 crash 실험은 없다.

## 2. CS: 엔디언으로 얻은 길이와 축소 변환

예제의 두 입력 바이트는 01 04, 파일 형식은 빅 엔디언이다. 올바른 해석으로 얻은 size_t length=0x0104는 260이다.

```c
size_t length = 0x0104;
uint8_t small = (uint8_t)length;
```

사용자는 표현 범위 때문에 다른 값으로 바뀐다는 원리를 회상했다. 교사가 260과 modulo 256을 제시한 뒤 small=4를 답했다. 이를 완전한 무힌트 회상으로 기록하지 않는다.

목적지 용량 16에 대해 검사는 small=4로 하고 실제 복사는 length=260으로 하면 검사값과 실제 사용값이 달라진다. 사용자는 4로 통과시켰는데 실제 260바이트를 복사해서 문제가 생긴다고 설명했다. 교사는 범위 밖 쓰기는 맞지만 반드시 crash한다고는 실행 없이 단정할 수 없다고 교정했다.

이 CS 사례는 문답이며 260바이트 범위 밖 복사를 실제 실행하지 않았다. 실제 사용할 길이를 변환 전 값으로 검사해야 한다는 이전 교정을 유지한다.

## 3. 복습: 실행 관찰과 정적 분석

사용자는 다음 두 근거를 구분했다.
- 프로그램의 반환값·목적지 AA 유지를 확인: 실제 실행 결과
- objdump로 call memcpy 앞뒤를 읽기: 정적 분석

objdump에 call이 존재해도 특정 입력에서 실행됐다는 뜻은 아니다. 사용자는 분기에 따라 call 여부가 나뉜다고 설명했다. 거부 경로가 호출을 건너뛴다는 정적 해석과, GDB 등에서 해당 실행의 분기·호출을 직접 관찰한 것은 구분한다. 새 GDB 동적 관찰은 없다.

## 4. 재현과 산출물

```bash
cc -std=c11 -Wall -Wextra -Werror -O0 -g zero_length_test.c -o zero_length_test
./zero_length_test > zero_length_results.txt
```

각 명령 종료 코드를 따로 확인한다. environment.txt와 sha256.txt에 실행 환경과 파일 식별 기록이 있다. 바이너리는 커밋하지 않고 재빌드한다.
