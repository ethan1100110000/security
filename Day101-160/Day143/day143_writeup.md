# Day143 — O0/O2 비교와 입력 길이

- 날짜: 2026-10-28 / W04 2/5
- 학습·재검증·기록 종료. 소스·원자료와 진도 로그를 함께 커밋한다. 시간은 측정하지 않았다.

## 메인: contains_zero 비교

입력의 앞 n바이트에서 0을 찾으면 1, 없으면 0을 반환하는 자체 함수를 별도 드라이버와 O0/O2로 빌드했다. LTO는 사용하지 않았다.

- `{41,00,42}`의 n=0/1/3 → 0/0/1.
- `{41,42,43}`의 n=3 → 0.
- `{41,42,43,00,44}`의 n=3/4 → 0/1.
- 두 버전의 총 6사례가 모두 예상과 일치했고 각 테스트 프로그램은 exit 0이었다. 반환값을 관찰했으며 읽기 횟수는 계측하지 않았다.

O0는 스택의 i와 n을 unsigned 비교해 i<n이면 반복한다. rbp를 저장한 뒤 프레임 기준으로 사용하고 공통 종료에서 복원한다. O2는 현재 주소와 끝 주소를 비교하며, 읽은 바이트가 0이면 즉시 반환한다. rbp를 건드리지 않으므로 저장·복원이 필요하지 않다. 경로 설명은 objdump 정적 분석이다.

명령 수 감소만으로 실제 속도를 확정할 수 없으며 성능은 측정하지 않았다. 시험한 입력의 결과 일치가 모든 입력의 동등성 증명은 아니다.

## CS: 파일 위치와 실행 주소

현재 주 드라이버 빌드에서 함수의 ELF 가상주소/파일 오프셋은 O0=0x1169, O2=0x12d0이었다. 포함 LOAD의 Offset과 VirtAddr가 모두 0x1000이라 이번에는 두 숫자가 같다. 일반식은 `파일 오프셋 = LOAD.Offset + (ELF 가상주소 - LOAD.VirtAddr)`이다.

두 빌드의 함수 위치 차이는 빌드 결과의 코드 배치 차이다. ASLR은 같은 파일을 실행할 때의 주소 배치에 영향을 준다. O0/O2 정적 위치 차이를 ASLR로 해석했던 답을 교정하고, 실행 전 재빌드의 파일 위치 변화 사례로 재검증했다. 초기 3사례 드라이버와 최종 4사례 드라이버의 빌드는 구분하며 주소 자료는 최종 주 드라이버 기준이다. 별도 boundary_test 바이너리에 이 주소를 적용하지 않는다.

## 복습: 용량과 실제 입력

함수의 n은 마지막 인덱스가 아니라 검사할 바이트 수다. 실제 읽을 수 있는 범위를 호출자가 보장해야 하며, 파일 입력만 검사하려면 버퍼 용량 대신 실제 입력 길이를 전달한다.

실제 stdin `ABCD` 4바이트를 0으로 초기화한 16바이트 버퍼에 읽었다. n=4는 반환0, n=8은 입력 뒤 초기값0을 발견해 반환1이었다. 둘 다 배열 안 접근이어서 ASan 접근 오류 없이도 논리 결과가 달랐다. 호출부의 requested8/received4 거부 조건도 확인했다.

첫 sanitizer 실행은 LeakSanitizer의 /proc 접근 실패로 exit1이었다. `ASAN_OPTIONS=detect_leaks=0`으로 누수 검사만 끈 재실행은 exit0이며 메모리 접근 검사는 유지했다. 이 결과가 모든 오류 부재를 보장하지는 않는다.

## 교정·근거

rbp를 안 바꾸면 저장 없이도 보존한다는 점, 성능 추측과 측정의 차이, 빌드 배치와 ASLR, 검사 개수와 인덱스, 버퍼 용량과 실제 입력 길이를 도움받아 교정했다. 새 조건에서 바이트 경계·주소 구분·입력7바이트의 n7/반환0 등을 재확인했다. 최초 무힌트 전부 정답으로 기록하지 않는다.

소스·결과·역어셈블·ELF 자료는 같은 폴더에 있다. 빌드: `cc -std=c11 -Wall -Wextra -Werror -O0/-O2 -g contains_zero.c <driver.c> -o <binary>`. sanitizer 옵션과 최초 실패·재실행 출력은 input_extent 관련 txt에 보존했다. 실행은 교사 Linux 컨테이너이며 GDB 동적 추적은 하지 않았다.
