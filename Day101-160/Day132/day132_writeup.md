## 1. 메인: 복사 함수의 입력 계약

처음 제시한 예제는 목적지 용량만 검사했다.

```c
int copy_data(char *dst, size_t capacity,
              const char *src, size_t length)
{
    if (length > capacity)
        return 1;

    memcpy(dst, src, length);
    return 0;
}
```

목적지는 살아 있는 쓰기 가능한 16바이트 배열, 원본의 실제 데이터는 4바이트, 복사 길이는 8바이트로 가정했다. 사용자는 목적지 검사는 통과하지만 입력 외 4바이트를 더 읽으므로 안전하지 않다고 답했다.

- 원본 객체 자체가 4바이트이면 8바이트 읽기는 객체 범위 밖 읽기다.
- 더 큰 살아 있는 배열에 실제 입력만 4바이트 있으면 객체 범위 안이어도 입력 계약을 벗어난 읽기다. 이것을 모두 객체 범위 밖 읽기로 부르지 않는다.

### 용량과 실제 길이
사용자는 처음 원본 배열 크기가 length보다 작으면 거부한다고 답했다. 원본 배열 용량 32와 실제 입력 길이 4가 다른 예제로, 실제 입력 길이 src_size를 별도 인자로 받도록 교정했다.

복사 함수가 받는 정보:
- dst: 복사 목적지 주소
- capacity: 목적지의 쓰기 가능한 용량
- src: 원본 시작 주소
- src_size: 처리 가능한 실제 입력 길이
- length: 이번에 복사할 길이

크기 관련 거부 조건:
```c
if (length > src_size)
    return 1;
if (length > capacity)
    return 1;
```

사용자는 src_size < length이면 거부하는 조건을 직접 작성했다. 변수명 오타를 교정했고, src_size >= length와 capacity >= length가 허용 조건이라고 답했다.

이 조건은 범위 관련 요구의 일부다. 포인터가 살아 있는 객체를 가리키고 필요한 접근 권한이 있으며, memcpy에 전달되는 원본·목적지 범위가 겹치지 않는 등 별도 전제도 필요하다. 오늘 그 전부를 새로 검증한 것은 아니다.

### 호출자의 책임
실제 입력은 4바이트인데 호출자가 src_size=32라고 넘기면 함수는 포인터와 전달된 숫자만으로 실제 길이를 복원할 수 없다. 사용자는 해당 검사만으로 잘못 전달된 크기를 알 수 없다고 답했다.

원본 배열 용량은 읽기 상한에 쓰고, 성공한 읽기의 실제 반환 길이를 복사 함수의 src_size로 전달해야 한다. 전체 입력을 여러 번 읽는 하네스라면 성공 길이를 누적해야 하며, 오늘 예제는 read 한 번의 반환값을 다뤘다.

## 2. 경계 테스트 설계

| src_size | capacity | length | 예상 | 확인하려는 경계 |
|---:|---:|---:|---|---|
| 4 | 16 | 4 | 허용 | 원본 실제 길이와 동일 |
| 4 | 16 | 5 | 원본 길이 검사에서 거부 | 원본 1바이트 초과 |
| 32 | 16 | 16 | 허용 | 목적지 용량과 동일 |
| 32 | 16 | 17 | 목적지 용량 검사에서 거부 | 목적지 1바이트 초과 |

사용자는 4/5와 16/17의 결과를 맞혔다. 목적지 검사를 따로 확인하려면 원본을 충분히 준비하여 앞선 원본 검사가 목적지 분기 관찰을 가리지 않게 한다.

위 표는 테스트 입력과 기대값 설계다. 실제 테스트 실행, 반환값 관찰, 분기 도달 증거는 아직 없다.

## 3. CS: signed/unsigned 변환과 read 오류

```c
char input[32];
ssize_t received = read(fd, input, sizeof(input));
```

사용자는 received=4이면 src_size=4를 전달하고, -1이면 오류라 그대로 길이로 전달하면 안 된다고 답했다.

size_t는 unsigned 정수형이다. -1을 size_t로 변환하면 SIZE_MAX가 되며 0으로 바뀌지 않는다. 사용자는 매우 큰 양수가 된다고 예상했다. 정확한 숫자는 size_t의 폭에 따라 달라지며 오늘 실측하지 않았다.

### 검사 순서 오류
```c
size_t n = (size_t)read(fd, input, sizeof(input));
if (n < 0)
    return 1;
```

n은 unsigned이므로 n < 0은 항상 거짓이다. 사용자는 -1이 큰 양수로 변환되어 오류를 잡을 수 없다고 설명했다.

### 올바른 순서
사용자가 signed 자료형으로 반환값 받기 → 음수 검사 → unsigned 변환 순서를 설명했고, 교사가 이를 코드로 정리했다.

```c
ssize_t received = read(fd, input, sizeof(input));
if (received < 0)
    return 1;

size_t src_size = (size_t)received;
```

“양수일 때 변환” 표현은 0도 포함한 “음수가 아닐 때 변환”으로 교정했다. 읽기 요청 크기가 0보다 큰 이번 예제에서 0은 EOF를 뜻한다. EOF가 애플리케이션의 유효한 입력인지 여부는 입력 계약에서 따로 판단한다.

사용자는 read를 복사로 표현했으며, read는 입력 읽기, memcpy는 버퍼 간 복사라는 역할을 교정했다. 위 오류 처리 예제는 단순화한 것이며 EINTR 재시도 등 전체 I/O 정책까지 구현한 것은 아니다.

## 4. 보안 2회독: 레지스터·분기·함수 반환

아래는 x86-64 Intel 문법의 개념 예제다. rsi=length, rdx=capacity를 가정한 것이며 앞의 C 함수가 해당 레지스터 배치를 사용하도록 실제 컴파일되었다는 뜻은 아니다.

```asm
cmp rsi, rdx
ja  reject

; 생략된 허용 경로

reject:
    mov eax, 1
    ret
```

### 비교와 분기
- cmp는 뺄셈 결과에 따른 플래그를 설정하며 두 피연산자 값을 변경하지 않는다.
- ja는 unsigned 비교에서 앞의 값이 뒤의 값보다 클 때 점프한다.
- jae는 크거나 같을 때 점프하므로 원래 length > capacity 검사와 경계 동작이 다르다.
- reject는 코드 위치에 붙인 라벨이며 반환값이나 내장 명령이 아니다.

사용자는 if(rsi > rdx)로 비교 방향을 맞혔지만 reject의 의미를 물었다. 라벨과 반환값을 구분한 뒤, 16과 16에서 ja는 점프하지 않고 jae는 점프한다고 답했다. cmp가 값 대신 플래그를 바꾼다고 답했다.

### 반환값과 복귀 주소
- mov eax, 1: int 반환값 1을 준비한다.
- ret: 스택의 복귀 주소를 이용해 호출자 코드로 돌아간다.
- 일반적인 x86-64 near ret 직전에는 복귀 주소가 [rsp]에 있다. ret은 그 주소를 rip에 넣고 rsp를 8 증가시킨다.
- call은 call 바로 다음 명령어의 주소를 스택에 저장한다.
- saved rbp는 이전 rbp 값이며 복귀 주소와 다르다.

```asm
call copy_data
mov ebx, eax
```

사용자는 ret의 역할을 “rsp 실행”으로 표현하고 복귀 주소를 saved rbp로 추측했다. rsp는 스택 위치 레지스터, rip는 실행 위치 레지스터라는 역할과 ret의 동작을 교정했다. call 다음에 실행할 명령을 물었을 때 mov라고 답했다.

반환값은 함수의 결과 데이터이고, 복귀 주소는 다음 실행 위치다. “함수 분기가 어디로 갔는지 알려주는 값”이라는 반환값 설명은 여러 분기가 같은 값을 반환할 수 있다는 예제로 교정했다. 사용자는 이유별 반환값이 구분되어 있지 않으면 같은 1만으로 거부 이유를 구분할 수 없다고 설명했다. 이유 판정에는 구분된 오류 코드·메시지 또는 실제 분기 관찰 등이 필요하다.

이 어셈블리는 설명용 코드로 실행하거나 GDB에서 관찰하지 않았다.

## 5. 오늘의 설명과 교정

사용자는 호출자가 원본 실제 길이, 원본 배열 용량, 복사 길이, 목적지 용량을 구분해야 하며, read 반환값을 signed로 받은 뒤 오류 검사하고 변환해야 한다고 정리했다. 원본 용량은 read 상한, 실제 길이는 복사 입력 계약이라는 역할을 교정했다.

이미 답한 두 범위 검사를 마무리에서 다시 요구하자 사용자가 반복을 지적했다. 앞선 답변을 완료 근거로 인정하고 같은 질문을 더 진행하지 않았다.

확인한 내용:
1. 실제 입력 길이와 원본 배열 용량 구분.
2. 원본과 목적지의 경계를 따로 겨냥한 기대값 설계.
3. read 오류를 unsigned 변환 전에 검사.
4. ja/jae의 경계 동작과 cmp의 플래그 설정.
5. 반환값·복귀 주소·saved rbp의 역할 구분.

다시 확인할 약점:
- ssize_t 검사에서 0을 제외하지 않기.
- 레지스터에 이름을 붙인 예제와 실제 호출 규약의 인자 배치를 구분하기.
- ret을 레지스터 실행으로 설명하지 않기.
- 반환값만으로 실제 분기와 오류 이유를 확정하지 않기.
