## 1. 메인: 두 조건이 동시에 잘못된 경우

공통 입력은 src_size=4, capacity=16, length=17이다. 원본과 목적지 범위를 모두 초과한다.

### 원본 우선
```c
if (length > src_size) return 1;
if (length > capacity) return 2;
```

첫 조건이 참이므로 반환값 1로 함수가 끝나고 목적지 검사는 실행하지 않는다. 사용자는 첫 검사에서 끝나므로 1이라고 설명했다.

### 목적지 우선
```c
if (length > capacity) return 2;
if (length > src_size) return 1;
```

같은 입력에 대해 반환값은 2가 된다. 복사는 두 코드 모두 실행하지 않는다. 사용자는 순서를 바꾸면 2로 반환한다고 예상했다. 함수 반환은 호출자의 실행 재개이며 프로그램 전체 종료와 다르다.

순서를 바꾼 코드에서 반환값 2가 나왔다고 원본 길이도 정상이라고 판단할 수 없다. 뒤의 원본 검사를 실행하지 않았기 때문이다. 검사 순서는 이 사례의 거부 여부를 바꾸지 않지만 어떤 오류를 먼저 보고하는지는 바꾼다.

## 2. 거부 전에 목적지를 바꾸는 실수

```c
dst[0] = src[0];
if (length > src_size) return 1;
if (length > capacity) return 2;
```

이번 테스트의 첫 바이트 접근은 유효하다. src는 실제 4바이트 배열, dst는 살아 있는 쓰기 가능한 16바이트 배열이며 src[0]=0x41, 실행 전 dst 전체는 0xAA다.

이 코드는 반환값 1은 맞아도 이미 dst[0]을 0x41로 바꾸었다. 따라서 정한 계약인 “거부 시 목적지 전체 무변경”을 어긴다. 모든 API가 이 계약을 제공하는 것은 아니지만 이번 함수에서는 명시한 요구다.

사용자는 처음 질문 맥락을 이해하지 못했다. 쓰기 → 검사 → 반환의 순서를 바이트 예시로 설명한 뒤 무변경 조건을 지키지 않았다고 답했다. 정상 코드와 잘못된 코드의 차이는 dst 초기 상태 비교에서 잡힐 것이라고 예상했다.

## 3. 실제 비교 실행

파일: rejection_test.c, rejection_results.txt.

| 변형 | 반환값 | 반환값 검사 | 목적지 무변경 검사 | 첫 바이트 | 거부 계약 |
|---|---:|---|---|---|---|
| 원본 검사 우선 | 1 | PASS | PASS | AA | PASS |
| 목적지 검사 우선 | 2 | PASS | PASS | AA | PASS |
| 검사 전 첫 바이트 쓰기 | 1 | PASS | FAIL | 41 | FAIL |

3/3 예상 동작을 관찰했다. 컴파일과 프로그램 실행 종료 코드는 모두 0이다. 마지막 행의 계약 실패는 의도적으로 넣은 잘못된 구현을 테스트가 발견한 결과다. 전체 프로그램은 “의도한 실패를 제대로 검출했는가”까지 판정하므로 종료 코드 0이 된다. 세 구현이 모두 올바르다는 뜻이 아니다.

반환값만 확인했다면 선행 쓰기 실수를 놓쳤을 것이다. 실제 비교는 memcmp(dst, before, sizeof(dst))로 목적지 전체의 최종 상태를 확인한다. 이 결과만으로 일시적 쓰기 후 복원까지 배제하거나 모든 부작용을 탐지한다고 주장하지 않는다.

### 실행 재현
```bash
cc -std=c11 -Wall -Wextra -Werror -O0 -g rejection_test.c -o rejection_test
./rejection_test > rejection_results.txt
```

각 명령의 종료 코드를 확인한다. 환경과 해시는 environment.txt, sha256.txt에 있다. 바이너리는 재빌드하며 커밋에는 소스와 원자료를 보존한다. sanitizer·퍼징·새 crash 검사는 수행하지 않았다.

## 4. CS: 정렬·캐스팅·바이트 복사

### 정렬 조건
4바이트 정렬을 요구하는 타입의 객체 주소는 4의 배수여야 한다. 사용자는 0x1000이 조건을 만족한다고 답했다. buffer가 0x1000에서 시작하면 buffer+1은 0x1001이므로 이 정렬 조건을 만족하지 않는다.

포인터 캐스팅은 기존 주소를 필요한 정렬 위치로 자동 이동시켜 주지 않는다. 정렬이 필요한 포인터 타입으로 캐스트했다고 올바른 정렬의 객체가 만들어지는 것도 아니다. 잘못 정렬된 포인터로 typed access가 허용된다고 가정하면 안 된다.

### 표현 교정: 타입과 객체 배치
교사가 “정렬이 보장된 타입”이라고 표현해 사용자가 uint32_t는 왜 정렬이 보장되는지 질문했다. 이를 다음과 같이 고쳤다.

- 타입에는 환경에 따른 정렬 요구가 있다.
- uint32_t value처럼 객체를 선언하면 컴파일러가 그 요구에 맞게 배치한다.
- 기존 바이트 주소를 uint32_t *로 바꾸는 것만으로 그 주소의 정렬이 보장되지 않는다.
- uint32_t가 32비트 크기라고 모든 환경에서 정렬 요구가 반드시 4라는 뜻은 아니다.
- C에서 _Alignof(uint32_t)로 요구를 확인할 수 있다. 오늘 이 값을 실제 출력하지 않았다.

int, double, 구조체 등도 각 타입의 정렬 요구가 있다. 정렬된 포인터 변수 자체와 그 포인터가 가리키는 대상의 정렬은 구분한다.

### 바이트 복사로 별도 객체에 읽기
```c
uint32_t value;
memcpy(&value, buffer + 1, sizeof(value));
```

원본에 sizeof(value)만큼 유효하고 읽기 가능한 바이트가 있고 목적지 객체가 살아 있다는 전제다. 원본을 uint32_t *로 역참조하지 않고 객체 표현 바이트를 복사한다. 실제 구현은 최적화될 수 있으며 memcpy가 반드시 바이트 명령으로만 실행된다는 뜻은 아니다.

사용자는 원본 주소를 옮긴 것이 아니라 데이터를 별도 변수에 옮겼다고 답했다.

### 정렬과 엔디언은 별개
memcpy는 바이트 순서를 보존하며 입력 형식의 엔디언 변환을 자동 수행하지 않는다. 리틀 엔디언 환경에서 12 34 56 78을 value의 객체 표현으로 복사하면 정수 값은 0x78563412가 된다. 사용자는 이 결과를 맞혔다.

오늘은 이 정렬 사례를 컴파일·실행하지 않았으며 Day134 엔디언 실행 결과와 구분한다.

## 5. 보안 2회독: 실제 memcpy 인자 준비와 거부 경로

대상은 Day134의 copy_data_disassembly.txt다. 새로 컴파일한 rejection_test의 레지스터 위치와 혼동하지 않는다.

```asm
mov rdx, [rbp-0x28]  ; length
mov rcx, [rbp-0x18]  ; src
mov rax, [rbp-0x8]   ; dst
mov rsi, rcx
mov rdi, rax
call memcpy
```

이 환경의 호출 규약에서 첫 세 정수/포인터 인자는 rdi, rsi, rdx로 전달된다. 사용자는 call 직전 rdi=dst, rsi=src, rdx=length를 직접 맞혔다. 즉 memcpy(dst, src, length)다.

원본 검사에서 return 1로 빠지는 경로는 eax=1을 준비하고 공통 leave/ret 위치로 이동한다. 위 인자 준비와 call memcpy에 도달하지 않는다. 사용자는 도달하지 못하고 끝난다고 답했으며 함수 반환과 프로그램 종료를 다시 구분했다.

이는 기존 바이너리의 정적 코드 흐름 해석이다. GDB breakpoint로 실제 call 비도달을 계측한 결과는 아니다. 오늘 실행된 비교 프로그램의 목적지 상태·반환값 관찰과 정적 해석을 구분한다.
