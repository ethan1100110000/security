# Day112 - AFL++ Instrumentation and Coverage

## 1. 계측 바이너리 비교

동일한 소스를 일반 Clang과 AFL++ 계측 컴파일러로 빌드했다.

```bash
clang -O0 -g -o day112_plain day112_target.c
afl-clang-fast -O0 -g -o day112_afl day112_target.c
```

두 바이너리의 일반 실행 결과는 같지만, `day112_plain`에는 AFL 계측과 forkserver가 없어 `afl-showmap` 실행 시 handshake가 실패했다. `day112_afl`은 edge를 통과할 때 coverage map의 counter를 갱신한다.

## 2. Edge coverage 확인

```bash
printf 'A' | afl-showmap \
  -o /tmp/day112_afl_map \
  -- ./day112_afl
```

`A` 입력은 전체 map size 11개 중 2개의 tuple을 실행했다. `A`와 `FUZZ`는 tuple 개수가 2개로 같았지만 coverage map hash가 달랐다. 따라서 tuple 개수만 같다고 동일한 실행 경로인 것은 아니며, 어떤 edge ID가 기록됐는지도 확인해야 한다.

## 3. 최적화 옵션 비교

```bash
afl-clang-fast -O2 -g \
  -o day112_afl_O2 day112_target.c
```

`-O0` 바이너리의 map size는 11, `-O2` 바이너리는 8이었다. 최적화 과정에서 basic block과 CFG가 합쳐지거나 재배치되면서 계측 지점이 달라질 수 있다. 따라서 서로 다른 최적화 옵션으로 빌드한 바이너리의 coverage 비율은 분모와 edge ID 공간이 다르므로 직접 비교하면 안 된다.

## 4. Hit-count coverage

입력 1바이트를 반복 횟수로 사용하는 `day112_loop`를 빌드했다.

```bash
afl-clang-fast -O0 -g \
  -o day112_loop day112_loop.c
```

`-e`는 edge 통과 횟수를 무시하고 실행된 edge ID 집합만 보여주며, `-r`은 각 edge의 실제 통과 횟수를 보여준다.

```bash
printf '\x01' | afl-showmap -q -e \
  -o /tmp/day112_loop_1_edge -- ./day112_loop

printf '\x14' | afl-showmap -q -e \
  -o /tmp/day112_loop_20_edge -- ./day112_loop
```

두 파일은 차이가 없었으므로 반복 횟수가 1과 20일 때 실행된 edge 집합은 같았다. 반면 `-r`에서는 같은 edge ID의 실제 통과 횟수가 각각 1과 20으로 나타났다.

AFL++은 정확한 횟수를 모두 구분하지 않고 다음 bucket으로 압축한다.

```text
1 | 2 | 3 | 4–7 | 8–15 | 16–31 | 32–127 | 128+
```

`20→24`는 같은 `16–31` bucket이므로 coverage 차이가 없었다. `15→16`은 `8–15`에서 `16–31`로 이동하므로 새로운 hit-count coverage로 확인됐다.

## 5. 결론

계측된 바이너리는 실행 중 edge별 counter를 coverage map에 기록한다. `afl-fuzz`는 실행 후 이 map을 누적 기록과 비교하며, 새로운 edge 또는 기존 edge의 새로운 hit-count bucket을 발견한 입력을 corpus에 보존한다.

실제 실행 순서가 달라도 edge ID와 hit-count bucket이 모두 같으면 AFL은 동일한 coverage로 판단한다. 따라서 coverage map은 효율적인 탐색 피드백이지만 전체 실행 이력을 완벽하게 표현하지는 않는다.
