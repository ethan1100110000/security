[실제 strtol 사용자 GDB 관찰]
메뉴 입력 "2abc": strtol 직후 RAX 2 (사용자 확인).
메뉴 입력 "abc2": strtol 직후 RAX 0 (사용자 확인).
출력된 unknown choice 분기는 사용자 추론과 일치. endptr는 NULL이므로 입력 완전성 검사는 없음.

[CS / 문답, 실제 코드 실행 아님]
uint8_t buf[8]={0x10,0x20,0x30,0x40,0x50,0x60,0x70,0x80}; buf=0x1000; p=buf+3.
n=6에서 p[n-1]=p[5]=buf[8], 접근 주소 0x1008 (범위 밖 읽기). 사용자는 OOB 판단은 맞았으나 처음 0x1002 주소 혼동; 설명 후 교정.
조건 변경 n=5에서 p[4]=buf[7], 접근 주소 0x1007, 값 0x80 (사용자 독립 정답).

[보안 복습 / Day083 write-up 대조, 실제 힙 재실행 아님]
원래 add→delete→show→edit→trigger의 show는 UAF로 callback의 원래 puts 주소 누출.
edit→show로 바꿔 callback까지 덮어쓰면 원래 puts leak 정보 소실.
조건 변경: edit 가능 범위를 data[0x20]로 제한하면 callback에 직접 쓰지 못함. 재할당/다른 쓰기가 없고 show가 callback 값을 노출한다는 전제에서 원래 puts leak 가능; callback overwrite는 불가능.
사용자 마지막 답: "음 leak은 되지만 덮어쓰기는 안된다".
※ freed chunk 시작부는 allocator metadata로 재사용 가능; data edit가 allocator 상태를 망가뜨릴 수도 있으므로 이후 malloc의 정상 동작은 보장하지 않음.
