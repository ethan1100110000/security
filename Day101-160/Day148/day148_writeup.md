## 계획과 완료 범위
현재 [일일 계획표](../../00_plan/hanyang-research-plan-2027.xlsx) Day148 메인은 '분기와 버퍼 크기·입력 바이트 길이를 GDB로 독립 추적', CS는 정수변환·배열 값/주소 추적, 복습은 이전 Pwn 풀이의 힌트 의존성 점검이다. 메인·CS·복습을 수행하고 사용자 관찰/교사 도움/미관찰을 구분해 기록한다.

- 대상: [Day147 archive_desk](../Day147/README.md), x86-64 Linux WSL + GDB/pwndbg. 같은 바이너리를 Day148의 새로운 입력 조건으로 분석.
- **증거 성격:** 원격 저장소의 전체 GDB 세션이 아니라 **사용자가 채팅에 올린 실행·역어셈블 출력 발췌**다. [관찰 발췌](day148_user_observations.txt) 참고.
- 실제 사용한 주요 명령/입력: `x/100i <PIE_BASE+0x141c>`, `b *0x5555555554d8` (strtol 후), `p/d $rax`, `b *0x5555555554bd` (fgets 후), `x/16bx $rbp-0x20`, `continue`, `bt`, `run < /tmp/day148_input.txt`. 런타임 주소는 해당 실행에서만 사용한다.

## 1. 메인: 메뉴 입력 → 정수 변환 → 분기
사용자가 독립적으로 찾은 핵심 명령:
```asm
0x5555555554ac: lea rax,[rbp-0x20]    ; 입력 버퍼
0x5555555554b0: mov esi,0x10           ; fgets size=16
0x5555555554b5: mov rdi,rax
0x5555555554b8: call fgets@plt
0x5555555554bd: test rax,rax
0x5555555554c0: je  0x55555555551c    ; EOF 또는 읽기 실패
0x5555555554c2: lea rax,[rbp-0x20]
0x5555555554c6: mov edx,0xa           ; base10
0x5555555554cb: mov esi,0x0           ; endptr=NULL
0x5555555554d0: mov rdi,rax
0x5555555554d3: call strtol@plt
0x5555555554d8: cmp rax,0x3
0x5555555554dc: je  0x555555555500
0x5555555554de: cmp rax,0x3
0x5555555554e2: jg  0x555555555507    ; signed greater
0x5555555554e4: cmp rax,0x1
0x5555555554e8: je  0x5555555554f2
0x5555555554ea: cmp rax,0x2
0x5555555554ee: je  0x5555555554f9
```

이후 사용자 역어셈블로 1→`call 0x2d8`(Preview), 2→`call 0x380`(Submit), 3→종료 경로, 그 외→`0x5507`의 `puts` 후 `0x5482` 메뉴 반복을 확인했다. `0x555555556099` 문자열 자체의 `x/s` 결과는 제출되지 않았으므로 `unknown choice` 문자열과의 대응은 출력/분기에서 유력한 해석으로 표기한다.

**실측·조건 변경**:
- `"2abc"` → `strtol` 직후 **RAX=2**를 사용자 GDB에서 확인, 메뉴 2로 분기 예상.
- `"abc2"` → **RAX=0**을 GDB에서 확인. 숫자를 하나도 읽지 못한 경우다.
- `"0"`도 RAX=0이 될 수 있으므로 반환값만으로 **정상적인 0과 변환 실패**를 구별할 수 없다. 현 코드의 `endptr=NULL`은 문자열 뒤쪽 문자 검사에 활용되지 않는다.

## 2. 메인: fgets의 16바이트 버퍼와 개행 잔류
`fgets(buf,0x10,stdin)`은 성공하면 **최대 15바이트 데이터 + 종료 NUL**을 기록한다. 입력을 `9`+14개의 `A`+`\n`으로 정하면, 첫 호출은 15개 문자만 담고 개행을 남긴다고 예상했다. 사용자는 최초에 개행이 남을 것이라고 정확하게 설명했다.

인터랙티브 실행에서 `unknown choice`가 한 번 출력된 뒤 다음 메뉴가 표시됐으나, 기대한 두 번째 breakpoint가 바로 관찰되지 않았다. `Ctrl+C`의 `bt`는 `#0 libc_read(fd=0,nbytes=1)`, `#5 _IO_fgets(n=0x10)`, `#6 0x5555555554bd`를 보여주었다. 이는 **메뉴 입력을 기다리는 중**이며 호출이 아직 반환되지 않았다는 증거다. 개행이 없다는 결론을 내릴 수 없다.

혼동을 줄이기 위해 파일 입력으로 재검증:
```sh
printf '9AAAAAAAAAAAAAA\n3\n' > /tmp/day148_input.txt
```
```gdb
b *0x5555555554bd
run < /tmp/day148_input.txt
x/16bx $rbp-0x20
continue
x/16bx $rbp-0x20
```

| 버퍼 바이트 | 첫 번째 fgets 반환 후 | 두 번째 fgets 반환 후 |
| --- | --- | --- |
| `buf[0]` | `0x39` ('9') | `0x0a` (LF) |
| `buf[1]` | `0x41` ('A') | `0x00` (NUL) |
| `buf[2..14]` | `0x41` ('A') | 이전 A가 잔존 |
| `buf[15]` | `0x00` | `0x00` |

두 번째 호출은 남아 있던 개행을 실제 소비했다. 버퍼 뒤의 A는 초기화되지 않은 이전 데이터이며, 두 번째 문자열은 `buf[1]`의 NUL에서 끝난다. **첫 키보드 실험의 'unknown choice 1회' 관찰은 그대로 보존**하되 파일 실험의 개행 소비 결과를 우선한 직접 증거로 쓴다. 파일 마지막 `3\n`의 최종 종료 출력은 제출되지 않았다.

## 3. CS: 배열 기점과 포인터 기점 구분
아래 예제는 **문답/손 추적**이며 새 바이너리 실행 자료가 아니다.
```c
uint8_t buf[8]={0x10,0x20,0x30,0x40,0x50,0x60,0x70,0x80};
uint8_t *p=buf+3;
size_t n=6;
if(n<=sizeof(buf)) printf("%02x\n",p[n-1]);
```

`buf` 시작 주소가 `0x1000`이고 `uint8_t` 원소는 1바이트라면 `p=0x1003`. `n=6`에서 `p[n-1]=p[5]=buf[8]`이므로 주소 `0x1008`은 OOB Read다. `n<=sizeof(buf)`만 확인하면 **p가 3바이트 이동한 사실**을 무시한다. 사용자는 OOB 여부는 독립적으로 맞혔지만 주소를 처음 `0x1002`라 적어 교정을 받았다.

새 조건 `n=5`에서는 `p[4]=buf[7]`, 주소 `0x1007`, 출력 `0x80`을 **추가 힌트 없이 정확히 답했다**. 이는 조건 변경 문답이며 직접 C 실행은 아님.

## 4. 보안 2회독: Day083 UAF leak → callback overwrite의 순서
과거 원격 저장소 [Day083 write-up](../../Day040-100/Day083/write_up.txt)과 대조했다. 그 기록에는 객체 `data[0x20]` 뒤 `callback = puts`가 있고, 해제 후 포인터를 초기화하지 않아 `show`에서 객체 raw memory 및 callback 값을 읽고, `edit`로 callback을 변경한 뒤 `trigger`하는 흐름이 있다.

- 기존 `add → delete → show → edit → trigger`: **show에서 원래 puts 주소를 먼저 leak**하고 이후 edit.
- 순서 교체 `add → delete → edit → show → trigger`: edit가 callback까지 덮으면 **원래 puts 주소를 잃으므로 기존 leak 전략이 깨짐**. UAF 자체가 사라진다는 의미는 아니다.
- 새 조건: edit를 `data[0x20]`에만 제한 → callback 저장 영역 `+0x20`을 직접 덮을 수 없음. 재할당이나 별도 수정이 없고 `show`가 callback 메모리까지 출력한다는 전제에서 **leak은 가능하나 callback overwrite는 불가능**. 사용자가 스스로 이 판단을 답했다. 단, freed chunk의 data 앞부분은 tcache metadata로 사용될 수 있어 편집 이후 allocator 무결성/후속 할당 성공은 보장하지 않는다.

교사가 먼저 `show` 동작과 callback/puts 역할을 다시 설명했고, 사용자가 유출 순서와 위험성을 회상했다. 마지막 조건 변경 답은 독립적으로 맞혔으나 전체 복습을 완전 무힌트로 평가하지 않는다. 오늘 Day083 힙 바이너리를 재실행한 것은 아니다.
