# Day156 / FINAL W06 4/4 — 블라인드 스택 분석 종합평가 (진행 중)

## 시험 자료
- 교사가 제작한 Linux x86-64 ELF `day156_target.elf`는 채팅 첨부 파일로 제공. 소스는 최초 독립 분석 종료 전 공개하지 않는다.
- SHA256: `616ff0a7e73176034294a9c3997c4d070a005a11d515417fbf59050e02a5f848`
- 로컬 격리 학습 대상. 교사 환경에서 정상/오류 입력의 동작을 사전 확인했으며, 사용자 실험 증거와 구분한다.
- 평가 목적은 취약점 원인과 메모리 안전성, 완화기법의 한계, 수정 원리의 검증이다. 셸 획득 등은 요구하지 않는다.

## 독립 심사
1. 입력 형식 및 유효성 검사와 처리 흐름을 복원.
2. 메모리 객체 경계와 입력의 영향 범위를 검증. 어떤 입력에서 어떤 현상이 실제로 나타나는지 확인.
3. 보호기법 확인 후 관찰된 동작/오류의 원인을 설명.
4. 코드와 런타임/메모리 근거 2종 이상 확보, 정상 입력과 경계 반례 비교.
5. 수정 방안과 회귀 테스트 제안. 가설/관찰/미확정 사항을 구분해 10분 분량의 분석 발표.
- 허용: file, checksec, readelf, objdump, Ghidra, GDB, Python 등 로컬 분석 도구. 정답/소스 열람 없이 독립적으로 수행.
- 교사 힌트가 필요하면 사용 사실 기록하고 다른 조건에서 무힌트 재검증.

## Git 배포 (2026-11-19)
- ELF 실행 파일을 Git에서 바로 재생성하도록 **무손실 압축된 바이너리**를 `day156_target.elf.xz.b64`에 올리고 `unpack.sh`를 추가했다. 원본 C 소스나 해답은 공개하지 않았다.
- WSL: `git pull --ff-only && cd Day101-160/Day156 && bash unpack.sh && ./day156_target.elf`
- `unpack.sh`는 Base64→xz 압축 해제 후 ELF를 복원하고, 위 SHA256과 일치하는지 자동 검증하고 실행 권한을 부여한다. 저장소에 인코딩 형태로 들어 있는 것은 **바이너리를 완전 복원하기 위한 배포 형식**이지 문제를 새로 컴파일하는 소스가 아님.
- 사용자 독립 분석 결과 제출 전. Day156 평가 아직 미완료.


## 학생 최초 독립 정적 분석 — 2026-11-19
- 학생이 Ghidra에서 첫 4바이트 헤더 및 이후 복사 데이터, 헤더 첫 2바이트 RV, 세 번째 값에 2를 곱한 memcpy 길이, 입력에 실제 존재하는 데이터 길이 검사와 목적지 용량 비교의 부재 가능성을 스스로 파악했다고 보고했다.
- 제출한 조건: `uVar2 == 0 || 0x18 < uVar2 || 3 < bVar1`. 학생이 조건의 의미와 `local_28 = 0x5b7d39a1` 초기화 및 memcpy 후 동일값 검사 목적에서 질문했다.
- 교사 보조 범위: 불리언 조건 읽기 및 검사값의 가능한 역할만 설명. 실제 스택 객체 경계와 오류 경로는 학생이 추가 증거로 직접 확인해야 한다. Ghidra 변수명만으로 원본 배열 선언 크기를 확정하지 않는다.
- 판정: 정적 입력 흐름 분석 진행 중. 실제 동적 실측, 스택 배치 근거, 보호 효과, 수정 방안 및 종합평가 아직 미완료.


## 사용자 동적 분석 — 정상 및 경계 반례
- 학생은 어셈블리에서 복사 시작 위치와 별도 무결성 검사 슬롯의 간격이 32바이트임을 확인했다고 보고. 허용 입력의 최대 복사량이 48바이트라는 점을 교사 질문 후 도출했다.
- 정상 입력은 교사 제공 바이너리 입력 생성 예로 실행하고 정상 통과했다고 구두 확인. 학생이 직접 구성한 최대 허용 길이의 입력으로 GDB에서 검사 슬롯이 A로 변경된 것을 확인했다고 보고. 이어 실행 시 **record integrity error** 출력이 Ghidra에서 확인한 오류 경로와 일치한다고 직접 보고.
- checksec 사용자 보고: Full RELRO, Canary, NX, PIE 활성화.
- 증거 수준: 어셈블리 위치와 GDB 관찰은 사용자 설명, 오류 문자열은 직접 보고. GDB 전체 덤프/종료 코드와 checksec 원문은 미제출. 목적지의 정확한 C 선언 크기는 아직 확정하지 않음.
- 교사 도움: 헤더 조건 해석, 바이너리 입력 생성 예, 정적 분석의 의미 및 디버거 명령 안내. 독립 분석과 도움을 구분한다. 학생은 쓰기 이후 검사라는 한계를 이해했으며, 다음 평가 단계는 오류 처리와 메모리 안전한 수정 방안, 경계 회귀 테스트 설명이다.


## 원인 및 수정 방안 구술 평가
- 학생은 최대 복사 범위가 컴파일러의 Canary까지 도달하지 않기 때문에 관측된 오류는 별도 무결성 검사에 의한 것이라고 설명했다. 교사 측에서도 배포 ELF의 해시와 디스어셈블리를 대조해 이를 확인하였다. 교사 확인은 사용자 독립 실측으로 기록하지 않는다.
- 학생은 복사 후 검사라는 한계를 설명하고, 복사 전에 목적지 배열 용량과 실제 복사량을 비교하는 수정안을 제시하였다. 수정 방향은 타당하다. 다만 근본 원인은 사후 검사 자체보다 **목적지 경계 검사의 누락**이며, 별도 무결성 검사를 제거하는 것은 수정의 필수 조건이 아니다.
- 교육상 다음은 정상 경계 및 초과 경계의 회귀 테스트 예상 결과를 설명하는 것. 소스 수준 수정의 실행 검증은 아직 수행하지 않았다.

## 수정안 검토 — 사전 목적지 경계 검사
- 학생이 원본 배열 선언 크기와 인접 슬롯까지의 거리를 구분해야 한다고 질문하여, 디컴파일 추정·정적 배치·동적 관찰의 증거 수준 차이를 설명함.
- 학생 독립 수정안: 복사 전에 `if (sizeof(목적지 배열) < uVar2 * 2)`가 참이면 종료. 실제 배열이 해당 스코프에 있고 기존 입력 검사를 유지한다면 타당. 포인터에 대한 sizeof는 배열 용량이 아니며, 복사량이 용량과 같으면 허용한다. 현 실습의 제한된 길이 범위에서는 곱셈 오버플로우 문제 없음.
- 수정 코드 실행 및 경계 회귀 테스트 실측은 아직 없음. 학생의 설계 답변과 실측을 구분함.

## 수정 설계 경계값 평가
- 실제 배열 용량 32B를 가정하고 사전 목적지 경계 검사를 적용할 때 학생 독립 답변: 30B 허용, 32B 허용, 34B 거부. 모두 정확. 이는 수정안에 대한 경계값 설계 검증이며 수정된 바이너리의 실제 실행 결과는 아니다.
- 메인 분석 평가의 정적/동적 관찰, 원인 및 수정 설계 답변 완료. 초기 단독 분석 후 헤더 해석, 입력 생성, 디버깅 및 원인 정밀화에 도움을 받은 사실은 유지. CS 구술 5문항 및 누적 복습, 증거/기록 마감은 아직 남음.
