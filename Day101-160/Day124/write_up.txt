# Day124 - TinyXML-2 Fuzz Harness 설계 및 검증

## 1. 목표

TinyXML-2의 메모리 입력 API를 직접 호출하는 AFL++ 하네스를 작성하고 다음 항목을 검증한다.

- 실제 입력 길이 전달
- 정상·비정상 XML 처리
- AFL 계측 및 Sanitizer 적용
- 입력별 coverage 차이
- 반복 실행 시 coverage 안정성
- 빈 입력, 중간 NUL, 최대 입력 크기 경계 조건

## 2. 대상

- Target: TinyXML-2
- Commit: `8224e427b655b83dae5e2298f1e6919523a78737`
- Target API:

```cpp
XMLError XMLDocument::Parse(const char* xml, size_t nBytes);
3. 하네스 입력 흐름
stdin
  -> read(STDIN_FILENO, buffer.data(), buffer.size())
  -> bytes_read 검사
  -> test_one_input(buffer.data(), bytes_read)
  -> XMLDocument::Parse(data, size)

하네스는 입력 버퍼의 시작 주소와 read()가 반환한 실제 길이를 파서에 전달한다.

strlen()은 중간 NUL에서 멈추고 NUL 종단이 없으면 범위 밖을 읽을 수 있으므로 사용하지 않았다.

4. 설계 결정
메모리 입력 API 사용
doc.Parse(reinterpret_cast<const char*>(data), size);

파일을 생성한 뒤 LoadFile()을 호출하는 방식보다 디스크 I/O와 파일시스템 의존성이 적다. 입력 주소와 실제 길이를 직접 전달할 수 있어 퍼징에 적합하다.

파싱 오류 처리

잘못된 XML에 대한 XML_ERROR_* 반환은 정상적인 입력 거부다. 이를 abort()나 crash로 처리하면 malformed XML이 모두 가짜 crash로 분류된다.

따라서 XML 파싱 성공과 실패 모두 하네스에서는 return 0으로 처리한다. 실제 메모리 오류는 ASan·UBSan이 탐지하도록 한다.

입력 상한
static constexpr size_t MAX_INPUT_SIZE = 1024 * 1024;

한 번의 read()로 최대 1 MiB만 처리한다. 이보다 큰 입력은 BOF를 발생시키지 않고 앞의 1 MiB만 읽으며 나머지는 처리하지 않는다.

6. Seed 검증

Day123에서 선별한 XML seed 12개를 디버그 하네스로 실행했다.

1~9번 정상 XML: XML_SUCCESS
10_bad_close.xml: XML_ERROR_MISMATCHED_ELEMENT(14)
11_bad_attribute.xml: XML_ERROR_PARSING_ATTRIBUTE(7)
12_unclosed_comment.xml: XML_ERROR_PARSING_COMMENT(10)

12개 모두 프로세스는 exit=0으로 정상 종료했으며 Sanitizer 오류는 없었다.

상세 결과는 seed_results.txt에 기록했다.

7. Coverage 검증

afl-showmap -e로 12개 seed의 edge coverage를 측정했다.

12개 모두 exit=0
모든 seed의 tuple 개수가 서로 달랐음
Sanitizer 오류 없음

예시:

Seed	Tuple count	Map SHA-256
01_minimal.xml	276	4e1c2659116dcd7c54510323f91cf455aeb5df6a78d9ab454727e742844a39d7
10_bad_close.xml	324	4e11315a90c2002b4835c920964b78d09a82553bd3528364fda8b89769112350

서로 다른 tuple 개수와 map hash는 입력들이 서로 다른 실행 경로를 만들었다는 증거다. 다만 이것만으로 모든 seed가 최종 corpus에 반드시 필요하다고 단정할 수는 없다. 전체 coverage 중복 여부는 이후 afl-cmin으로 확인해야 한다.

전체 결과는 showmap_summary.txt에 기록했다.

8. Coverage 안정성

정상 입력 01_minimal.xml과 비정상 입력 10_bad_close.xml을 각각 5회 실행했다.

각 seed는 5회 모두 동일한 coverage map hash를 생성했다. 표본 실행 기준으로 같은 입력에서 실행 경로가 안정적으로 재현됐다.

상세 결과는 stability_summary.txt에 기록했다.

9. 경계 조건
빈 입력
전달 크기: 0
결과: XML_ERROR_EMPTY_DOCUMENT
프로세스: exit=0
Sanitizer 오류 없음

빈 문서는 XML 파싱 오류지만 취약점은 아니므로 정상 종료했다.

중간 NUL

입력:

<root/>\x00<<<<
실제 전달 크기: 12바이트
결과: XML_SUCCESS(0)
프로세스: exit=0

하네스와 Parse(data, size)에는 전체 12바이트가 전달됐지만 TinyXML-2의 실제 파싱 로직은 첫 NUL을 문자열 끝으로 처리했다. 따라서 NUL 뒤의 잘못된 <<<<는 문법 검사 대상이 되지 않았다.

이는 길이 전달이 불필요하다는 뜻이 아니다. 명시적인 길이는 입력의 복사 경계를 보장하지만, 중간 NUL의 의미는 대상 파서의 내부 동작에 의해 결정된다.

1 MiB 초과 입력
원본 입력 크기: 1,048,608바이트
하네스가 읽은 크기: 1,048,576바이트
결과: XML_ERROR_PARSING_TEXT(8)
프로세스: exit=0
Sanitizer 오류 없음

read()의 세 번째 인자가 버퍼 크기이므로 버퍼보다 많은 데이터를 쓰지 않는다. 초과한 32바이트는 읽히지 않았다.

10. 결론

TinyXML-2의 메모리 입력 API에 입력 주소와 실제 크기를 전달하는 AFL++ 하네스를 작성했다.

정상·비정상 XML, 빈 입력, 중간 NUL, 최대 입력 크기를 검증했으며 정상적인 파싱 실패가 가짜 crash로 처리되지 않음을 확인했다. AFL, ASan, UBSan 계측과 반복 실행 coverage 안정성도 확인했다.

Day124에서는 하네스 작성과 검증까지만 완료했다. 실제 afl-fuzz 실행과 corpus minimization은 아직 수행하지 않았다.
