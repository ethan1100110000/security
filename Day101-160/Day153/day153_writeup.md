# Day153 — FINAL W06 1/4 — stripped ELF 분석, 스택 오염 검증, ASan 비교

> 날짜: 2026-11-16 (KST). 대상: 실습용 로컬 stripped ELF `target_elf`, 추가 ASan 비교 모델 `asan_repro.c`. 이 기록은 학생이 채팅에서 제출한 실제 관찰, 교사 설명/제공 모델, 추론을 구분한다.

## 목표와 방법
- 낯선 x86-64 Linux stripped ELF의 입력 경로·길이 검사·스택 쓰기를 분석하고 실제 메모리 오염의 효과를 증명한다.
- Ghidra 디컴파일로 구조를 복원하고 objdump 어셈블리와 대조, GDB/Pwndbg에서 정상 입력과 오염 입력을 비교한다.
- ASan 계측된 **별도 재구성 C 모델**에서 오류 발생 위치 차이를 설명한다. 시스템 호출 규약 7~9번째 정수 인자를 컴파일된 어셈블리로 확인한다.
- Day043/Day050 스택 정렬 복습과 바꾼 조건을 판단한다.

## 1. 프로그램 정적 복원 — 사용자 분석
- `_start`의 `__libc_start_main` 인자에서 `main` 후보 주소 `0x4012e9` 확인.
- `main`은 `puts`, `read(0,input,0xc0)`, 비양수 결과에 대한 `no input` 처리, 양수이면 helper `0x401176` 호출로 이어진다는 분석.
- helper는 읽은 길이가 8 미만이면 `short record`(-1), 첫 4바이트가 `PXN1`과 다르면 `bad marker`(-2)로 종료한다고 분석.
- header 레이아웃: `"PXN1"` 4B, 리틀엔디언 unsigned 16비트 `a`(offset 4), `b`(offset 6), 데이터(offset 8부터).
- 사용자가 찾은 유효성 검사: `a <= 112`와 `a <= read_count - 8` — 첫째는 입력 형식 길이 상한, 둘째는 실제 원본 입력 데이터가 `a`바이트 이상 존재하는지 확인.
- `memset(local,0,0x30)`, `memcpy(local,input+8,a)`. 이후 `i<a && i<0x30` 범위의 바이트 합산 후 `printf("accepted: mode=%u sum=%u",b,sum)`, 성공시 0 반환.
- 정확한 **배열 선언 크기**는 소스 없이 확정하지 않았다. `read(...,0xc0)`은 최대 읽기 길이(192B)이고 배열 선언 크기의 증거가 아니다. `memset(...,0x30)`은 초기화된 48B의 크기이지 선언된 배열 용량의 충분한 증거가 아니다. Ghidra의 임의 생성 로컬 크기(메인 약 200B, helper 약 60B)는 도구의 추정이다.
- 주의: 초기에 사용자 구두로 메인의 `rbp-0x58`을 언급한 부분은 이전 `main`의 `rbp-0xd0` 관찰과 상충. helper의 `[rbp-0x58]`에 있는 입력 포인터 슬롯과 혼동했을 가능성. 독립 프레임 구분이 필요하며 확정적 메인 스택 배열 오프셋으로 쓰지 않는다.

## 2. GDB — 인자와 정상 복사 검증
`0x401285`의 `memcpy@plt` 직전 학생 실측:
```
rdi 0x7fffffffde60
rsi 0x7fffffffdec8
rdx 0x20
```
- 첫 입력 형식: `PXN1` + `a=32` + `b=0` + `A×32`, 총 40B.
- `RDI=dest`, `RSI=input+8`, `RDX=a=32`; 복사 실행 뒤 목적지 32B가 `0x41`로 변했다고 사용자가 직접 보고. 입력값이 복사 크기를 제어함을 동적 확인.

## 3. GDB — 오버플로우와 지역변수 변조
둘째 입력 형식: `PXN1` + `a=80` + `b=0` + `A×80`, 총 88B.

복사 시작은 `dest=[rbp-0x50]=0x7fffffffde60`. 사용자 직접 제출한 `dest+48`부터 32B의 복사 전/후 덤프:
```text
before
0x7fffffffde90: 00 00 00 00 00 00 00 00
0x7fffffffde98: 90 df ff ff 00 00 50 00
0x7fffffffdea0: 00 00 00 00 00 00 00 00
0x7fffffffdea8: e0 e2 ff f7 ff 7f 00 00

after
0x7fffffffde90: 41 41 41 41 41 41 41 41
0x7fffffffde98: 41 41 41 41 41 41 41 41
0x7fffffffdea0: 41 41 41 41 41 41 41 41
0x7fffffffdea8: 41 41 41 41 41 41 41 41
```
- 원래 `a` 슬롯 `[rbp-0x12]`, `b` 슬롯 `[rbp-0x14]`는 목적지 시작으로부터 각각 +0x3e, +0x3c. 모두 이번 80B 복사 범위 내.
- 복사 후 `x/2hx $rbp-0x14` 사용자 실측: `0x7fffffffde9c: 0x4141 0x4141`.
- `continue` 사용자 실측: `accepted: mode=16705 sum=3120`.
  - `mode=16705=0x4141`: `b=0` 입력이 로컬 슬롯 오염으로 바뀐 결과.
  - `sum=3120=65×48`: `A` 값 0x41을 최대 48회 더한 값.
- **메모리 오염이 프로그램의 관측 가능한 출력까지 변경하는 사실**을 검증.

## 4. GDB — saved frame/return address 오염과 예외
- `dest=[rbp-0x50]`: saved RBP 시작 오프셋 `0x50`; 복귀 주소 시작 오프셋 `0x58`. 복사 길이 81B부터 saved RBP 첫 바이트, 89B부터 반환 주소 첫 바이트, 96B면 반환 주소 8B 전부까지 덮을 수 있다.
- 학생은 `a=96` 입력 실험에서 `[rbp+8]` 복사 전 주소 `0x0000000000401353`, 복사 후 `A`로 덮인 사실을 보고.
- `continue` 후 사용자 직접 제출:
```text
rip 0x4012e8
rsp 0x7fffffffdeb8
rbp 0x4141414141414141
x/i $rip   => 0x4012e8: ret
x/gx $rsp  => 0x7fffffffdeb8: 0x4141414141414141
```
- 사용자 독립 설명: `ret`가 `RSP`가 가리키는 값을 복귀 대상으로 사용하려 할 때 오염된 값 때문에 오류가 난다. `0x4141414141414141`은 x86-64 비정규 주소이므로 `ret` 자체에서 예외가 나 RIP가 해당 `ret` 위치에 남을 수 있다. **RIP가 0x4141…로 성공적으로 이동했다는 주장은 하지 않는다**.
- 위 결과는 스택의 saved return address까지 제어 가능한 쓰기가 도달하고 반환 절차가 실패한 실측. 정확한 원본 로컬 배열 선언 크기는 이 실험만으로 별도로 확정하지 않음.

## 5. ASan 비교 — 교사 제공 별도 모델임을 명시
- 별도 파일 `asan_repro.c`는 **원본 ELF 소스가 아닌** 학생이 복원한 처리 구조를 흉내 낸 교사 작성 독립 C 모델이다. 이 모델에서는 로컬 배열을 **48B로 가정**한다.
- 모델 컴파일: `gcc -O0 -g -fsanitize=address -fno-omit-frame-pointer asan_repro.c -o asan_repro`.
- 사용자 로컬에서는 최초 `probe32.bin` 미존재, `probe80.bin` `bad length`로 입력 생성 문제를 확인한 뒤, 길이 32/80 및 총 파일 길이 40/88인 입력을 재생성하고 실행이 "이제 정확하네"라고 보고. **정상 출력/ASan 오류의 전체 원문은 채팅에 제출되지 않았으므로 수치 직접 실측으로 기재하지 않는다**.
- 교사 별도 환경에서 같은 모델의 `a=32`은 정상 출력 `accepted: mode=0 sum=2080`, `a=80`은 `stack-buffer-overflow`/`WRITE of size 80`로 계측 결과를 관찰했으나 사용자/원본 바이너리 실측과 구분.
- 사용자 개념 설명: 일반 실행은 메모리 오염 이후 사용 시점(이번 경우 `ret`)에 문제가 드러날 수 있지만 ASan 계측은 배열 경계 초과 쓰기 시점에 진단 가능. 개념 확인 통과. ASan의 검출 범위는 계측·redzone 등 구현 조건에 좌우되며 모든 종류의 메모리 오류를 검출하지는 못한다.

## 6. CS — System V AMD64 정수 인자 7~9개
사용자는 `abi9.c`의 `test(long a,...,long i)`를 컴파일 후 objdump에서 직접 읽어 제출:
```asm
1169: mov rdx,QWORD PTR [rbp+0x10] ; g, 7번째
116d: mov rax,QWORD PTR [rbp+0x18] ; h, 8번째
1171: add rdx,rax
1174: mov rax,QWORD PTR [rbp+0x20] ; i, 9번째
```
- 인자 1~6은 RDI,RSI,RDX,RCX,R8,R9, 이후 정수 인자는 스택을 사용한다.
- 함수 진입 시 `[rsp]`은 복귀 주소; `push rbp; mov rbp,rsp` 뒤 `[rbp]`은 이전 RBP, `[rbp+8]`은 복귀 주소, `[rbp+0x10/0x18/0x20]`은 7~9번째 인자. 컴파일된 어셈블리 확인 완료(별도 GDB 동적 ABI 실측은 하지 않음).

## 7. 복습 — Day043/050, 16바이트 스택 정렬
- 조건1: 함수 진입 직후 `RSP%16=8`; `push rbp; mov rbp,rsp; sub rsp,0x28; call printf`. 사용자 첫 답 "만족함"은 오답. 교사 추적 후 `push`에서 0, `sub 0x28`에서 다시 8로 돌아가 `call` 직전 16B 정렬 미충족임을 교정.
- 조건2: `sub rsp,0x20`으로 변경. 사용자 답 "만족함" 정답. `push rbp` 후 0, `sub 0x20` 후에도 0으로 `call` 직전 정렬 충족.
- Git 원문 대조:
  - [Day043](../../Day040-100/Day043/write_up.txt): `win` 진입 `RSP%16=0`일 때 `ret` 가젯 추가로 8이 되어 셸 상호작용 성공.
  - [Day050](../../Day040-100/Day050/write_up.txt): `ret` 가젯 포함 시 win 진입 정렬 실패, 가젯 제거 후 성공.
- 호출 직전 ABI 정렬은 `RSP%16=0`, 일반적인 `call`에 의해 복귀 주소가 스택에 기록되면 **피호출 함수 진입 시 `RSP%16=8`**. ROP의 별도 `ret` 가젯 하나도 `RSP`를 8B 변화시키므로 상황별로 추가/제거 여부가 다르다. **첫 오답과 교사 힌트, 바뀐 조건 정답을 구분 기록**.
