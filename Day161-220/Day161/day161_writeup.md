## 1. 학생 최초 실행 출력 (채팅으로 제출, 원본 Git 세션 확인 전)

학생 원문:

```text
session=0x02df2f4577c8c93a
trace[0]=0x5be72258428d
trace[1]=0x790e07280e10
trace[2]=0x4227
one opaque packet (max 208 bytes; CR/LF rejected)
frame accepted
```

학생 첫 관찰: `주소같은게 나오넹` (주소처럼 보인다는 가설. 각 필드가 주소인지, 어떤 매핑의 주소인지, 재현 시 어떻게 변하는지는 아직 검증 안 됨.)

교사 관찰 분류(학생 증거 아님): `trace[0]`·`trace[1]`는 64비트 포인터 형태를 띠지만 실측 매핑/반복 실행 없이 ELF/libc로 확정하지 않는다. `session`은 16진수 식별값일 수 있고 `trace[2]`는 작은 수로 정수·offset·부분 주소 등 미확정. `frame accepted`는 단순 입력 수락이며 목표 기능 실행 성공으로 인정하지 않는다.

## 2. 학생 Ghidra 독립 정적 분석 — 최초 해석 (채팅 보고, 원본 캡처 미확인)

학생 보고 원문(요지):
1. `session`은 `getpid()` 결과에 `(uVar1 & 0xffff) ^ 0x16573548c902` 비트 연산으로 만들어진 값.
2. `trace[0]`는 프로그램 내부 함수 주소로 보여 PIE Base 계산에 활용 가능하다는 추론.
3. `trace[1]`는 `puts` 주소인 듯하다는 가설.
4. `trace[2]`에는 내부 함수 정적 주소 `0x1227`이 관련되며 첫 실행 `0x4227`, 다른 실행 `0x9227`로 보였다. 이 함수는 `main`에서 직접 호출되지 않는다고 보고.

판정: 사용자는 단순 출력 관찰 이후 Ghidra 호출 근거로 필드를 분리했음. `session`은 이 정적 해석이 사실이면 프로세스 ID 유래 값이지 즉시 메모리 주소로 간주할 수 없음. `trace[0]`를 PIE 기반 계산에 쓰려면 바이너리 내 정확한 함수 오프셋과 동일 주소 출처를 교차 검증해야 함. `trace[1]`을 libc leak으로 쓰려면 `puts` 포인터 표현과 현재 libc 매핑을 확인해야 함. `trace[2]`의 `0x...227` 공통 부분 및 실행별 상위 부분 변화는 **단편/마스킹된 주소 또는 변환 결과 가능성**을 보여 주지만 아직 정확한 C/Ghidra 표현식은 학생이 제시하지 않았음. **정적 디컴파일과 런타임 맵을 구분하며 확정 판정 보류.** 교육용 바이너리 정답이나 목표 분기/입력 구성은 교사가 사전 공개하지 않음.

### 학생 2차 독립 분석 — `trace[0]` 오프셋과 `trace[2]` 디컴파일 표현

학생이 Ghidra에서 `trace[0]` 관련 내부 함수 주소를 `0x128d`라고 특정함. 최초 실행 `trace[0]=0x5be72258428d`과의 베이스 연산 교차 검증 예정.

학생의 Ghidra 복원소스 보고 원문: `printf("trace[2]=0x%04llx\\n",0x1227);`. 학생이 "뭔지 모르겠다"고 질문함. 첫 실행 실제 `trace[2]=0x4227`, 다른 실행 `0x9227` 보고와 **겉보기의 literal 0x1227이 모순**. 교사 질문: (1) 같은 실행에서 `trace[0]-0x128d`로 PIE base를 계산, (2) 이 base에 `0x1227`을 더한 뒤 결과의 낮은 16비트를 `trace[2]`와 비교. `%04llx`의 4는 최소 표시 폭일 뿐 4자리 절단이 아니라는 점 구분. Ghidra의 `printf` 직전 어셈블리에서 실제 `rsi` 전달값·비트마스크 또는 주소 연산을 확인하기 전에는 단정하지 않음. **학생에게 정답 숫자/목표 함수는 아직 공개하지 않음.**

### 학생의 `trace[2]` PIE 연관성 자력 추론 (채팅 보고)

학생 원문: `어 아 뭔지 알겠네 0x1227 오프셋만 출력하는게 아니라 base를 더하고 하위 4비트 출력이구나`.

교사 판정: **PIE base를 더한 동적 주소의 하위 4개 16진 자리를 관찰했다는 취지는 타당하나**, "하위 4비트"는 엄밀히 4 bits = 1 hex digit이라 잘못된 단위이며 4자리 hex는 **16 bits**. 앞서 학생이 제출한 `trace[0]=0x5be72258428d` 및 `trace[0] offset 0x128d` 가정에서 `base=0x5be722583000`, `base+0x1227=0x5be722584227`, 하위 16 bits `0x4227`로 출력과 합치. 다만 `printf("%04llx", 0x1227)` 정적 Ghidra 표현만으로 실제 masking 연산이 증명되지는 않았으며 출력 직전 실제 인자 값/명령어를 확인해야 한다. 이 계산은 **교사 검증**으로, 학생이 숫자를 직접 제출하지 않았음.

### 학생의 입력·스택 프레임 독립 분석 (채팅 제출; 실측 미검증)

학생 보고:
- 패킷에 `\\r` / `\\n` 금지, 일반 `frame accepted`는 목표 성공이 아니라는 판단.
- `main`에서 직접 호출하지 않는 내부 함수(정적 `0x1227`)를 통제 흐름의 **목표 후보**로 가설 설정. 함수 의미/성공 분기 아직 증명하지 않음.
- 스택 카나리 비활성 확인했다고 보고. `read` 최대 `0xd0`(208) 바이트를 수신, 반환 길이를 하위 함수 인자로 전달, 길이 검사 없는 `memcpy`로 로컬 배열 `[rbp-0x60]`에 복사한다는 디스어셈블리 관찰 보고. 로컬 버퍼의 **실제 크기 및 memcpy 호출까지 도달하는 분기**는 현재 대화에 명령 출력 미제출.
- `[rbp-0x64]`에 `0x43434343`을 저장하며 조건 검사가 있는 듯하다고 보고. 버퍼 시작 `rbp-0x60`보다 주소가 낮아 정방향 복사에서는 단순 연속 덮어쓰기 범위 밖이라는 판단. 그러나 이 변수의 값 검사/분기 자체가 정상 흐름 또는 성공 조건에 중요할 수 있어 **'무시 가능'은 유보**.

다음 검증: 함수의 정확한 스택 메모리 배치, 복사 크기와 스택 리턴 주소까지 거리, `memcpy` 전후 제어 분기/경계 검사, 제한된 입력으로 RIP 제어 가능 여부를 **학생이 독립 검증**. 교사는 오프셋·목표/가젯 정답을 아직 공개하지 않았고, 성공 판정은 보류.
### 학생의 saved RIP 거리 계산 및 입력 조건 재점검 (채팅, 동적 미검증)

학생 원문: `1. 0x68바이트 패딩 2. 조건 뭐 없는디? 입력에 \\r \\n 이 없어야하는거`.

- 정방향 `memcpy`의 대상 시작이 `rbp-0x60`, saved RIP가 `rbp+8`인 통상 프레임이라면 RIP 위치까지 거리는 정확히 `0x68`(104) bytes. RIP 전체를 마커 8B로 채우면 총 `0x70`(112) bytes로 읽기 최대 `0xd0`(208) 내에 들어간다. **이는 Ghidra 기반 정적 거리 계산이며 동적 saved RIP overwrite 실증은 아직 미제출**.
- 학생의 경로 분석상 `CR/LF` 거부 외 길이 비교 등 명시적 조건이 없다고 보고. 독립 원본 디스어셈블리 출력은 미제출이므로 "검증된 조건 없음"으로 확정하지 않는다. 과잉 재검사 요구 대신 명시 조건 충족하는 112바이트 단일변수 마커 입력으로 saved RIP 변화 및 종료 시점 관찰 예정.
- `rbp-0x64` 확인 변수는 정방향 overwrite 대상 바깥쪽이라는 논리는 타당하나 제어 흐름상의 의미는 별도. 학생은 먼저 saved RIP 단독 오염 가능성을 실증해야 하며 목표 함수로의 분기/성공은 아직 확정하지 않는다.

### Saved RIP overwrite 동적 검증 — 학생 확인 보고

교사가 제안한 112B 프로브(패딩 `0x68` bytes + 8B 마커)를 GDB에서 실행한 다음 학생이 `ㅇㅇ 덮이는거 확인했엉`이라고 **요약 보고**했다. 따라서 `0x68` 가설의 saved RIP overwrite를 학생이 직접 관찰했다고 기록한다.

**증거 수준:** 실제 GDB 메모리·레지스터 출력이나 원격 Git 학생 세션 로그는 아직 확인하지 않았다. 그러므로 정확한 RIP/스택 워드 값, 예외 발생 위치·종류, 다음 함수 진입/성공을 입증했다고 기재하지 않는다. 현재 판정은 `RIP 제어 관찰 보고 — 원본 대조 대기`.

다음 단계는 내부 `0x1227` 후보 함수의 분기와 인자, 성공 조건을 학생이 디스어셈블리에서 복원하는 것. 즉시 해당 주소로 점프하는 payload를 정답으로 가정하지 않는다.

### 학생의 후보 함수 0x1227 -> 0x11d4 호출 경로 최초 복원 (채팅 원문)

학생은 Ghidra에서 후보 내부 함수 `0x1227`가 `0x11d4`를 `param_1=1`로 호출한다는 경로를 발견했다고 보고. `0x11d4` 복원 코드 학생 제출:

```c
void FUN_001011d4(int param_1)
{
  if (param_1 == 1) {
    write(1,"PROOF_FAIL: entry boundary\n",0x1b);
  }
  else {
    write(1,"PROOF_FAIL: register contract\n",0x1e);
  }
  /* WARNING: Subroutine does not return */
  _exit(2);
}
```

학생 가설: `param_1!=1`인 분기는 별 의미 없고, `0x11d4`로 반환주소를 조작해 `rdi`를 바꿀 수 있다는 추론. **교정:** 두 분기 모두 `PROOF_FAIL`을 출력하고 공통 `_exit(2)`로 종료하므로 단순히 `rdi`를 변경해 `0x11d4`에 진입하는 것은 로컬 성공 조건을 만족하지 않는다. 현 시점에 `0x1227` 전체 함수 본문·성공 경로·통제된 실행 결과를 제시하지 않았고, `0x11d4`를 목표라고 판정할 수 없다. 다음 학생 독립 과제: 두 분기의 종료 결과 예측과 `0x1227` 전체 디컴파일/호출 직전 분기를 재점검. 보이지 않는 성공 경로를 교사가 가정해 답을 공개하지 않음.

### 학생의 0x1227 전체 함수 본문 확인 (2026-11-27, Ghidra 학생 보고)

학생이 Ghidra에서 본 `FUN_00101227` 전체 코드(원문):

```c
void FUN_00101227(void)
{
  FUN_001011d4(1);
  return;
}
```

이전 단계에서 `FUN_001011d4(1)`은 `PROOF_FAIL: entry boundary`를 출력하고 `_exit(2)`를 호출하는 **비반환 실패 경로**로 확인했다. 따라서 0x1227 함수의 **정상 진입은 실패로 끝나며**, 안에 숨은 조건 분기가 있을 것이라는 교사의 이전 가능성 제시는 이 소스에 대해서는 지지되지 않는다. Ghidra의 `return`은 실제 `_exit` 이후 도달 불가한 표현이다. 0x1227이 출력 trace에 노출되었다고 해서 성공 목적지라는 뜻이 아니다.

다음 학생 독립 탐색: Ghidra 문자열 전체 목록과 `PROOF_FAIL` 외 성공·중립 메시지의 XREF를 추적하고, 진입 가능한 **별도 제어 흐름/출력 경로**를 근거로 찾아야 한다. 교사는 아직 실제 성공 함수·가젯·주소 정답을 공개하지 않음.
### 학생이 PROOF_OK 경로 발견 (2026-11-27, Ghidra 정적 관찰)

학생이 문자열 검색 후 **학생 직접 발견**한 함수:

```c
void FUN_001011a9(void)
{
  write(1,"PROOF_OK: gated control-flow verified\n",0x26);
  /* WARNING: Subroutine does not return */
  _exit(0);
}
```

정적 의미: 이 함수에 **실제로 진입해 `write`와 `_exit(0)`까지 수행되면** 성공 표식과 종료 상태 0이 나온다. 기존 `0x1227`은 `PROOF_FAIL: entry boundary` 경로이므로 성공 진입점으로 보지 않는다. 하지만 `0x11a9` 시작 주소로 제어를 넘기는 것만으로 평가 의도인 **gated control-flow**를 충족하는지는 아직 입증되지 않았다. `0x11a9` 호출 XREF, 호출 이전 분기·레지스터·스택 경계 조건을 학생이 직접 확인한 뒤 실험으로 검증 필요. 교육용 정답 페이로드/ROP 체인은 교사가 선제 제공하지 않음.

### 성공 함수 XREF와 디컴파일 출력의 모순 (학생 독립 관찰)

학생 보고: Ghidra에서 `FUN_001011a9`의 참조를 열자 참조 함수가 `0x1227`로 나타났지만, 학생이 앞서 본 `FUN_00101227`의 디컴파일에는 `FUN_001011d4(1)`만 있어 성공 함수 참조가 보이지 않았음.

판정: **모순을 아직 해결하지 않음**. Ghidra의 함수 소속(XREF origin), 참조 종류(`CALL`, `JUMP`, `DATA` 등), 참조가 시작되는 **정확한 명령어 주소**와 instruction bytes가 필요하다. 디컴파일러는 호출 불가능하다고 추정한 코드(특히 `_exit` 같은 noreturn 호출 뒤)를 생략할 수 있으므로, Listing 디스어셈블리와 raw `objdump -d`를 대조할 것. 단지 XREF가 있다고 해서 `0x1227` 정상 진입에서 성공에 도달함을 의미하지 않음. 교사는 정답 경로를 공개하지 않고 학생에게 해당 XREF의 실제 참조 위치·명령어를 먼저 확인하도록 안내.
### 학생이 Listing에서 숨겨진 성공 분기 독립 발견 — `0x1227` (2026-11-27)

```asm
-- Flow Override: CALL_RETURN (CALL_TERMINATOR)
```

이는 학생이 **이전에 보았던 디컴파일 `FUN_00101227(){FUN_001011d4(1);return;}`의 불완전한 요약을 반증**하는 정적 증거. `0x1227`은 단순 실패용 함수가 아니라 조건부 검증 게이트의 진입점으로, `RSP&0xf==8`, `RDI==실제 런타임 문자열 주소 (PIE+0x2020)`, `RSI==rol64(*(uint64_t*)(PIE+0x4160),9)^0x3a7b19`, `RDX==0x68d` 네 조건을 모두 통과하면 직접 `jmp` `0x11a9` 성공 함수로 연결됨. `LEA`는 문자열 **값이 아닌 주소** 비교임. **이 판정은 교사의 Listing 해석이고 학생은 Listing 발견까지 독립 수행했으며 네 조건을 본인 언어로 설명하는 구술 아직 미제출.**

참고로 해당 Listing에는 Ghidra의 `Flow Override: CALL_RETURN (CALL_TERMINATOR)` 문구가 있으므로 Decompiler에서 조건들을 누락한 원인과 연관된 설정/추정인지 확인할 가치 있음. 실제 동적 게이트 통과와 로컬 PROOF_OK는 아직 미제출. 다음 학생 단계: 가장 어려운 미확인 변수가 `DAT_00104160`이 어디서 채워지는지와 `session` 출력과의 관계, 그리고 `ret` 기반 진입 시 RSP 정렬을 독립 확인하는 것. 교사는 완성 가젯·페이로드·정답 스크립트를 공개하지 않는다.

### 학생이 session 값과 전역 데이터 주소 연계 확인 (Ghidra, 최초 해석)

학생 원문: `그러면 rsp % 16 == 8 이어야 하고 rdi는 저 문자열이 있는 주소 보니까 0x2020임 rsi는 session으로 출력되는값인거같은데 printf("session=0x%016llx\\n",DAT_00104160); 16바이트 출력이니까`.

학생 독립 성과: 스택 정렬 조건과 `RDI`의 문자열 ELF 오프셋 `0x2020`을 찾아냄. `session` 출력에 `DAT_00104160`이 직접 사용되는 사실을 Ghidra에서 확인하여, 성공 게이트가 읽는 qword과의 데이터 출처를 연결함. 교사 보정: `%016llx`는 **16개의 16진수 문자(64 bits = 8 bytes)를 최소 너비/0-padding으로 출력**할 뿐 "16바이트 출력"은 아님. 또한 `RSI`의 목표값은 `DAT_00104160`의 원시값 자체가 아니라 Listing의 `rol64(session,9) XOR 0x3a7b19`; `RDI`는 실행 주소 `PIE base + 0x2020`. **학생의 실제 런타임 값 계산·ROP 체인·검증은 아직 제출 전**.

### 학생 독립 ROP 가젯 탐색 — 다중 pop 선택 (채팅 제출)

학생 보고: `pop rdi`, `pop rsi`, 독립 `ret` 가젯을 찾았으며, `pop rdx; ret`은 없고 대신 `pop rdx; pop r13; ret` 가젯을 발견했다. 학생이 **추가로 소비하는 r13에 더미 값이 필요**하다고 스스로 판단.

판정: 가젯의 명령 순서가 보고대로라면 스택에서 `RDX 값`, `R13 더미`, `다음 RIP`를 차례로 소비한다. 전체 스택 진행은 8B×3=24B, 가젯 진입 전후 `RSP%16`이 바뀌므로 목표 함수 `0x1227` 진입 조건 `RSP%16==8`을 **전체 체인 기준으로 다시 계산**해야 함. 더미에 제약된 CR/LF 바이트가 포함되지 않아야 하고 `r13`이 나중에 사용되는지 확인 필요. 가젯의 실제 주소/원본 disassembly와 실행 페이로드는 아직 제출되지 않았으므로 독립 구현 성공 판정 전이다.

### Day156 D+7 ABI 지연복습 — 첫 무힌트 답변 (2026-11-27)

문제: 프레임 포인터 없이 함수 진입 `RSP=0x1008`; `push rbx; sub rsp,0x20; ...; call helper; add rsp,0x20; pop rbx; ret`. 7/8번째 정수 인자 상대 위치, `call` 직전 정렬, callee-saved `RBX` 위반/복구 설명.

학생 원문: `rsp + 0x10 , 0x18인가 2. 0 만족 3. 그 뭐냐 이름이 레지스터 보존 어쩌구 기존 rbx의 값을 스택에 넣어놓고 함수에서 rbx사용 끝날때 스택에 있던 기존값을 다시 rbx에 넣음`.

판정: **① 오답**. `0x10/0x18`은 함수 초입 정렬·push·sub 변화 이후의 현재 `RSP` 기준으로 맞지 않음; 정확한 상대 offset은 `+0x30/+0x38` (callee entry `RSP+8/+16`, 현재 `RSP=0xfe0`). 학생에게 처음에는 정답 offset을 전달하지 않고, `0x1008→0x1000→0xfe0`와 최초 복귀주소 슬롯을 기준으로 새로 계산하게 함. **② 정답:** `call` 직전 `RSP=0xfe0`, `RSP%16=0`. **③ 개념 정답, 명칭 미회상:** `RBX` callee-saved 레지스터, 호출받은 `helper`가 이를 복구하지 않고 바꾸면 ABI 위반. 바깥 함수의 `push/pop`은 자신의 호출자에게 보여 줄 `RBX` 보존이며 helper의 위반을 정당화하는 것은 아님. 학생 재계산 및 새로운 조건 재평가 전까지 **Day156 D+7 복습 미통과(① 교정 중)**.

### Day156 D+7 스택 인자 보정 — 학생 2차 답변 (2026-11-27)

학생 재답변 원문: `rsp + 0x28 + 0x10, 0x18 이네`. 프롤로그의 `push rbx`(8B) 및 `sub rsp,0x20`(32B)로 인한 총 `0x28`B 변화는 바로 잡았으나, 함수 **진입 시** 7·8번째 정수 인자 위치를 각각 `[entry_rsp+0x10]`, `[entry_rsp+0x18]`로 둔 상태라 결과 `[rsp+0x38]`, `[rsp+0x40]`은 **각각 8B 과대**. 실제 함수 진입 시 return address=`[entry_rsp]`, argument7=`[entry_rsp+8]`, argument8=`[entry_rsp+16]`. 따라서 현재 rsp=`0xfe0`에서 각각 `0x1010-0xfe0=0x30`, `0x1018-0xfe0=0x38`. 중간 계산을 갖춰가는 것은 진전이나 아직 무힌트 재검증 통과 아님. 짧게 기준을 교정한 뒤 후속 새로운 조건에 적용하도록 안내.

### Day156 D+7 변경 조건 독립 재검증 (2026-11-27)

문제: 진입 `RSP=0x1008`, `push rbp; mov rbp,rsp; push rbx; sub rsp,0x30`. 현재 RSP 기준 7/8번째 정수 인자 위치 구하기.

학생 무힌트 변경 조건 답: `rsp + 0x48 , rsp + 0x50` — **두 값 모두 정확**. 현재 `RSP=0x1008-8-8-0x30=0xfc8`, 7번째 인자 원래 슬롯 `0x1010` → `+0x48`, 8번째 `0x1018` → `+0x50`. 직전 프레임 포인터 없는 변형에서는 오답 후 교정받았으므로 **D+7 판정은 '교정 후 새로운 조건 재검증 통과'**이지 첫 시도 무힌트 통과가 아님. SysV ABI 정렬 및 RBX callee-saved 개념은 최초 설명 정답(정확한 명칭만 재제시)으로 기록됨.
