## 실패 1: 잘못된 free 순서

### 목표
첫 번째 malloc에서 a를 다시 받기

### 실행 순서
free(a)
free(b)
p = malloc(0x30)

### Heap 상태
free(a): tcache[0x40] → a → NULL
free(b): tcache[0x40] → b → a → NULL

### 증상
p == b

### 원인
tcachebin은 LIFO방식을 사용 free 순서가 잘못되어 p == b가 되었다
p == a를 만들려면 a를 나중에 free해야 함

### 검증
- tcachebins: b -> a -> 0
- raw memory:
  - b+0x00 = Safe-Linking으로 인코딩된 a
  - a+0x00 = Safe-Linking으로 인코딩된 NULL = a >> 12

## 실패 2: Double Free Abort

### 실행 순서
a = malloc(0x30)
free(a)
free(a)

### 증상
abort 오류 발생

### 원인
free된 a chunk에 있는 tcache key를 확인 두 번째 free에서 key가 일치하면 bin을 순회 동일한 chunk를 발견
abort 오류

### 첫 번째 free 이후 상태
- tcache[0x40]: a -> 0
- a+0x00: a >> 12
- a+0x08: tcache key

### 검증
- abort 로그: free(): double free detected in tcache 2
- GDB 종료 신호: SIGABRT
- 두 번째 free 직전 tcachebins: a -> NULL
- raw memory:
  - a+0x00 = a >> 12
  - a+0x08 = tcache key

### 추가 실험: key 변조
a+0x08의 key를 0으로 덮고 다시 free하면 abort를 우회할 수 있었고,
tcache count는 2, decoded next는 a를 가리켜 a -> a 자기참조 상태가 됐다.

## 실패 3: 잘못된 libc base

### 잘못된 계산
wrong_base = puts_leak - system_offset
wrong_system = wrong_base + system_offset

### 증상
base가 틀려서 이후 base로 계산한 libc함수 전부 틀림

### 실제 호출
잘못된 계산은 사실상
wrong_base = puts_leak - system_offset
puts_leak = wrong_base + system_offset 즉,
puts_leak = wrong_system

system(/bin/sh) 인 줄 알았지만 실제 호출은
puts(/bin/sh)

puts
### 원인
puts_leak에서 puts_offset을 빼지 않고 system_offset을 빼서 base계산

### 검증
- page alignment: 하위 12바이트 000정렬
- vmmap: libc 매핑 시작과 계산한 값이 같음
- assertion: libc_base + libc.symbols["puts"] == puts_leak
